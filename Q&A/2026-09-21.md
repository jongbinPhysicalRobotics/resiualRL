## Q1. (교수님 피드백) sin 스윙궤적은 탕 튀거나 내리꽂는 식이 된다

> 다른 팀 발표에서 나온 지적. 베지어로 보완하면 될 것 같다. **수정은 하지 말고 인지·기록만.**

### 지적이 정확히 맞고, 우리는 이미 재봤다

sin 아치 `z = h·sin(πs)` 의 양 끝 속도는 `±h·π/T_sw` 로 **0 이 아니다**:
- 이륙(s=0): **+0.457 m/s** ← "탕 튀는" 것
- 착지(s=1): **−0.457 m/s** ← "내리꽂는" 것 (T_sw=0.344, h=0.05 기준)

9/16 Q3 에서 실측: sin 아치 명령 −0.457 / 실제 −0.512 m/s.

### 현재 상태 — `--softland` 가 양 끝을 이미 0 으로 만든다

| | 이륙 v_z | 착지 v_z |
|---|---|---|
| sin (코드 **기본값**) | +0.457 | −0.457 |
| `--softland` (권장 구성) | **0** (smoothstep) | **0** (Hermite, v_td=0) |

권장 구성엔 이미 들어 있다. 다만 **코드 기본값은 아직 sin** (`soft_land=False`) 이라
플래그 없이 돌리면 교수님이 지적한 그 궤적이 나온다.

### 베지어와의 관계 — 9/16 Q3 에서 정량 비교함

같은 경계조건(v_to=v_td=0, 정점 5 cm)으로 5차 베지어와 우리 2단 곡선을 비교하면
**양 끝은 정확히 일치**하고 최대 편차 1.74 cm 는 스윙 중반(s=0.73). 접촉 구간 편차는
0.4~0.6 cm 로 실측 추종오차(1.6~5.6 cm)에 묻힌다.
→ **곡선족은 무관, 경계조건이 전부.** 베지어로 바꿔서 얻는 건 **`v_to` 파라미터**
(의도적 이륙속도로 초반 clearance 확보 — 현재 0.89 cm 로 빠듯) 하나다.

> **정리**: 교수님 지적 = 우리 9/16 Q3 결론과 일치. 착지 쪽은 해결됐고, 이륙 쪽
> `v_to` 는 미검증 후보로 남아 있다. 오늘은 수정 안 함.

## Q2. (교수님 피드백) dt = 0.02, 즉 50 Hz 까지는 잘 나와야 한다

> **인지·기록만.**

### 현재 우리 주기

| | 값 |
|---|---|
| 물리 시뮬 | 500 Hz (dt 0.002) |
| 토크 갱신 (Jᵀ·임피던스) | 500 Hz |
| **MPC 재풀이** | **100 Hz** (`DECIM=5`) |
| MPC 지평 이산화 `DT_MPC` | 0.05 s × 16 = 0.8 s |

"dt=0.02" 는 **재풀이 주기**로 읽는 게 자연스럽다 (지평 이산화는 이미 0.05).

### 참고 근거 둘

- **배포 RL 정책은 50 Hz** (`control_decimation=10` × 0.002) 로 1.28 m/s 를 간다 (9/17)
- Residual MPC 논문 Fig. 7: MPC 를 **25 Hz** 로 내리면 학습이 크게 나빠진다 (100 Hz 필수)
  → 50 Hz 는 그 사이. 논문은 50 Hz 를 시험하지 않았다

### 시험 방법 (나중에)

`--decim 10` 한 플래그. 현재 QP 평균 7.8 ms / p99 11.7 ms 라 **계산 여유는 50 Hz 에서
2.5배**로 늘어난다. 붕괴한다면 계산이 아니라 **지연 위상여유**(PHYSICS_MAP 230행:
자세루프 ~3 Hz, 지연 ~25 ms) 문제일 것.

**뷰어 오버레이** (`--view`): 스윙 중인 발의 참조궤적을 **선 24개**(왼발 초록·오른발 파랑),
현재 목표를 **작은 구**, 착지점을 **빨간 구**로 그린다. `mjv_initGeom`+`mjv_connector`,
`v.user_scn` 사용. 뷰어 없이 독립 `MjvScene` 으로 검증함 (스윙 중 26 geom/발).

### 첫 플롯이 바로 보여준 것 (0.5 m/s, 10 s)

**① 토크 스파이크가 눈에 보인다.** hip_pitch 가 **스윙마다 한 번씩 −200 N·m** 까지 튀고
이용률이 **2.4배**. 9/17 Q5 에서 "초과는 100 % 스윙 임피던스" 라고 잰 그것이
이제 그림으로 보인다.

**② 스윙 추종오차가 톱니다.** 이륙 때 0 → 착지 때 **4~5.6 cm** 로 단조 증가.

스윙 중에 쓸리기 때문이다 (9/16 Q1: 14 cm) — **과녁이 움직여서 생기는 오차**라는
9/16 §4 의 결론과 정확히 맞는 모양이다.

**③ 솔브타임은 이봉(bimodal).** 서 있을 때 ~5 ms, 걸을 때 ~8 ms (활성 제약 증가).
이 10 s 구간엔 임계 초과 스파이크 없음 (최대 20.5 ms).

**④ R_my 가 +20 N·m 까지** — 피치 CoP 예산 +16.4 N·m(Fz=327 기준)를 넘는 순간이 있다.
Fz 가 그때 더 크긴 하지만 **피치 CoP 포화가 그림에서 보인다.**

## Q4. 스윙궤적 기준점 — 사각형(발바닥) 중심으로 잡을까?

> 내 의견 → **발 site(발목 원점) 유지. 이유 셋.**

### ① 제어기가 추종하는 점이 발목이다

`SwingController.wrench()` 는 `mj_jacSite(발 site)` 로 자코비안을 구하고 거기에
임피던스를 건다. **궤적은 제어기가 실제로 움직이는 점에 정의해야** 추종오차가
의미를 갖는다. 사각형 중심에 궤적을 정의하고 발목을 제어하면 "명령한 점 ≠ 제어한 점".

### ② 발이 수평이면 두 점은 상수 오프셋이다

스윙 제어기가 발바닥을 수평으로 유지하므로(z축 정렬 모멘트), 발바닥 중심은
발목에서 **앞 3.5 cm · 아래 3.5 cm 고정** (`x_c = 0.035, h = 0.035`, 발 frame).
궤적·추종오차 **그림 모양이 같고 위치만 평행이동**한다. 정보가 늘지 않는다.

### ③ 사각형 중심은 "다른 질문"의 답이다

Caron CWC 가 사각형 중심을 쓰는 건 **접촉 wrench 의 기준점**(힘이 어디에 작용하나)이
그래야 식이 닫히기 때문이다 (9/18 Q3). 스윙궤적은 **기구학적 목표**(발이 어디로 가나)다.
같은 점을 쓸 이유가 없다.

### 그래도 발바닥 중심이 필요해지는 경우

- **발이 스윙 중에 피치**하면 발가락·뒤꿈치 clearance 가 발목 높이와 달라진다
  (험지, 계단). 그땐 `foot_pos` 에 발가락·뒤꿈치 z 를 따로 추가 (3줄)
- 착지 목표 `z_ground = 0.0331` 은 이미 "발바닥이 닿을 때의 발목 높이"라
  오프셋을 품고 있다 — 지금은 문제없음

> **적용**: 뷰어·로그 모두 **발 site 기준**. 코드 주석에 근거 명시.
> 이 프로젝트의 반복 교훈(닫힌 루프를 불필요하게 건드리지 않기)과도 맞는다.

## Q5. 착지~stance 구간의 u 로그 분석 — 접촉이 제대로 안 되는 것 아닌가?

> 새 스크립트 [12_contact_analysis.py](../MPC/src/12_contact_analysis.py).
> 스케줄 착지 시각을 t=0 으로 43개 스텝을 정렬해 평균.

### 결론: **접촉은 빨리 된다. 문제는 "하중 인계(handoff)"에 구멍이 뚫리는 것.**

### 1. 접촉 확립 자체는 문제가 아니었다

| | 값 |
|---|---|
| 실제 접촉까지 지연 | 평균 **6.0 ms**, 중앙값 4.0, 최대 12.0 |
| 미접촉 이벤트 | **0 / 43** |
| stance 전체 실현율 (실측/명령 Fz) | **98 %** |
| 초기 50 ms 실현율 | 99 % |

> 9/16 Q3 의 "8.5 ms 늦게 닿는다"는 맞았지만, **그 자체는 병목이 아니다.**
> 100 ms 이후로는 명령과 실측이 ±5 N 으로 붙고 `my` 도 거의 완벽히 추종한다.

### 2. ★ 그런데 착지 후 첫 100 ms 가 심하게 진동한다

| 스케줄 대비 | 착지발 실측 | 반대발 실측 | **합계 / 체중** |
|---|---|---|---|
| −8 ms | 0 N | 325 N | 99 % |
| **0 ms** | **0 N** (명령 **219 N**) | 310 N | 95 % |
| +16 ms | 336 N | 88 N | **130 %** |
| +48 ms | 250 N | 58 N | 94 % |
| **+64 ms** | **104 N** | **0 N** | **⚠ 32 %** |
| **+72 ms** | **466 N** | 0 N | **142 %** |
| +96 ms 이후 | ~330 N | 0 N | ~100 % (안정) |

**+64 ms 에 양발 합력이 체중의 32 % 로 떨어진다 — 몸이 순간적으로 거의 자유낙하한다.**
그리고 8 ms 뒤 142 % 로 내리꽂힌다. 합력 최대는 평균 **160 %**, 최악 **191 %**.

### 3. 기전 — 인과 사슬

1. **스케줄 착지 시각에 MPC 가 공중의 발에 219 N 을 명령** (실측 0 N, 발 높이 1.4 mm)
   — `Fz ≥ 10 N` 제약 때문에 QP 가 그 발에 하중을 배분한다
2. 그 명령이 `−JᵀW` 로 **다리를 아래로 가속**시킨다 (임펄스 219 N × 6 ms ≈ 1.3 N·s,
   다리 7.2 kg 기준 Δv ≈ 0.18 m/s — 원래 착지속도 0.048 m/s 의 4배)
3. 6 ms 뒤 접촉이 생길 때 **여분의 운동량**이 있어 Fz 가 오버슛 (명령 236 → 실측 323 N)
4. 오버슛 → **발이 튄다** (관통 −1.1 mm → 반발 +2.2 mm)
5. 그 사이 **반대발은 스케줄대로 +56 ms 에 떠난다** (DS = 2·sf−1 = 14 % = 112 ms/주기,
   착지 후 몫은 56 ms)
6. **+64 ms: 새 발은 튀어올라 104 N, 반대발은 0 N → 합력 32 %** — 몸이 떨어진다
7. 떨어진 몸이 발을 다시 눌러 **466 N (142 %)**, ~96 ms 에 안정

> **명령 합력은 내내 327~374 N (≈체중) 으로 정상이다.** 계획이 아니라 **실현**의 문제다.

### 4. 배포 RL 정책과 비교 — 정반대 성향

| | 착지 v_z | **합력 최대** | **합력 최저** |
|---|---|---|---|
| **우리 MPC** (0.5) | **−0.048 m/s** | 160 % (최악 191) | **⚠ 32 %** |
| 배포 RL (0.5) | −0.490 m/s | 208 % (211) | **92 %** |
| 배포 RL (1.0) | −0.001 m/s | 226 % (232) | 70 % |

**우리는 10배 부드럽게 착지하는데(−0.048 vs −0.490) 하중이 끊긴다.**
**그들은 세게 착지하지만 하중이 한 번도 92 % 아래로 안 내려간다.**

> **즉 "부드러운 착지"를 얻고 "연속적인 하중 인계"를 잃었다.**
> 9/16 Q3 에서 `--softland` 도입 후 저속 pitch 가 후퇴한 것의 진짜 정체가 이것으로 보인다.
> (그때는 "접촉률 42→0 %" 로만 봤는데, 실제로 아픈 건 **합력 32 % 구멍**이다)

### 5. 무엇을 고쳐야 하나 — 우선순위 수정

9/16 Q3 에서 "접촉 인지 계층" 3종(Fz,min 램프 / 실측 접촉 N_lock / 지면 탐색)을 적었는데,
**이 측정은 그중 어느 것이 급한지를 가른다**:

1. **★ `Fz,min` 램프가 1순위** — 착지 직후 `Fz ≥ 10 N` 을 즉시 요구하지 말고
   `α(t)·Fz_min` 으로 올린다. 사슬의 **1번 고리(공중 발에 219 N)를 끊는다**
2. **이중지지 구간 재검토** — 반대발이 뜨는 시각(+56 ms)이 새 발의 하중 인수보다 이르다.
   `sf` 를 키우면 DS 가 늘지만 9/17 데이터는 반대(고속일수록 sf ↓)를 가리킨다.
   → **램프로 인수를 앞당기는 쪽이 먼저**
3. 실측 접촉 기반 스케줄 보정은 그다음

> ⚠ 이 프로젝트 전례상 **증상을 직접 누르면 하중받던 것이 드러난다.**
> `v_td` 로 착지속도를 키우는 건 이미 실패했고(9/15), 이번 데이터도
> **충격이 아니라 연속성이 문제**라고 말하므로 그 방향은 여전히 아니다.

## Q6. `J̇q̇` 를 넣어봤다 — **6번째 "증상 억제의 역설"**

> "어차피 큰 도움이 안 된다면 그냥 정의를 잘 사용하는 게 맞을 것 같다"
> → 타당한 원칙이라 구현. **그런데 '도움이 안 되는' 게 아니라 '손해'였다.**

### 1. 구현

`mj_jacDot` 이 MuJoCo 3.12 에 있고 비용도 **1.5 us** (500 Hz 발 2개 = **+0.15 %**).

```python
rhs = [a_ff, 0]
if self.jdot:
    mujoco.mj_jacDot(m, d, jdp, jdr, d.site_xpos[sid], m.site_bodyid[sid])
    rhs -= np.vstack([jdp, jdr])[:, dofs] @ d.qvel[dofs]    # p̈ = J q̈ + J̇ q̇
qdd = lstsq(J6, rhs)
```

### 2. 의도한 효과는 **났다**

| vx | `J̇q̇` | **z 추종오차** | **스윙토크 최대배** |
|---|---|---|---|
| 0.5 | 켬 | **0.21 cm** | **2.31** |
| 0.5 | 끔 | 0.25 | 2.53 |
| 0.6 | 켬 | **0.21** | **2.41** |
| 0.6 | 끔 | 0.24 | 2.55 |

z 추종 **16 % 개선**, 스윙토크 첨두 감소. 앞서 예측한 방향 그대로.

### 3. ★ 그런데 횡 진동이 **5/5 속도 전부** 악화한다

40 s A/B, 다섯 속도:

| vx | y진폭 (jdot) | y진폭 (off) | **변화** | 실측 v (jdot / off) |
|---|---|---|---|---|
| 0.2 | 3.4 | 3.4 | **+0 %** | 0.199 / 0.199 |
| 0.3 | 3.6 | 3.3 | +6 % | 0.306 / 0.307 |
| 0.4 | 3.6 | 3.3 | +10 % | 0.410 / 0.412 |
| 0.5 | 5.2 | 4.2 | +23 % | 0.494 / 0.496 |
| **0.6** | **7.1** | 5.4 | **+32 %** | **0.462 / 0.494** |

**평균 +14 %, 5/5 악화, 그리고 속도에 단조 증가.**
120초 배터리(0.3/0.5/0.6)도 전부 생존은 하나 같은 경향.

> 단조 증가가 결정적이다 — 궤적 의존 노이즈라면 이렇게 깔끔하게 속도에 비례하지 않는다.

### 4. 기전 추정 — **횡 여유가 없어서 드러난다**

- `J̇q̇` 보상은 `q̈` **평균을 68.5 → 79.0 으로 키운다** (첨두는 267→220 으로 줄이지만)
- `M` 은 밀집이라 `M q̈` 는 **stance 다리·골반 행에도** 값을 만든다
  → 평균이 커지면 **stance 로 가는 교차항도 평균적으로 커진다**
- 그런데 **롤 CoP 는 0.3 m/s 부터 이미 포화**(이용률 1.13, 9/18 Q4). 여유가 없다

**0.2 m/s 에서 차이가 정확히 0 인 것이 이 해석을 지지한다** — 그 속도엔 횡 여유가 있다.
즉 `J̇q̇` 가 틀려서가 아니라 **닫힌 루프의 횡 마진이 바닥이라 어떤 교란도 증폭**된다.

### 5. 판정 — **기본 꺼짐, 플래그 보존, 보폭 후 재시험**

```
--jdot     (opt-in, 기본 꺼짐)
```

- **식 자체는 `--jdot` 쪽이 옳다.** 주석에 근거와 측정치를 남겼다
- 지금 끄는 이유는 "틀린 식이 좋아서"가 아니라 **"현재 닫힌 루프가 그쪽에 co-adapt 돼
  있고, 정확한 식이 요구하는 횡 마진이 지금 없어서"**
- **1순위 보폭 축소(27→16 cm)로 횡 CoP 여유가 생기면 결론이 바뀔 수 있다.**
  그때 이 표를 그대로 다시 돌릴 것

> **이 프로젝트에서 6번째**다: capy / LIP-exact / td_mode / 제약 frame / 상체 SRB / **J̇q̇**.
> 다만 앞의 다섯과 성격이 다르다 — 앞의 것들은 **제어 법칙·제약 집합**을 바꿔
> 평형점을 옮겼지만, 이건 **피드포워드 한 항**이고 문제는 그 항이 아니라
> **그 항을 감당할 마진이 없다는 것**이다. **조건부 보류**로 기록한다.



### 6. (같은 날 추가) 보폭 13 cm 위에서 재시험 — **여전히 보류**

§5 에서 "보폭 축소로 횡 여유가 생기면 결론이 바뀔 수 있다"고 했다. Q7 로 보폭을 13 cm 로
줄인 뒤 같은 A/B 를 다시 돌렸다 (40 s):

| vx | 실측 v (jdot / off) | y 진폭 (jdot / off) | roll σ (jdot / off) | y 변화 |
|---|---|---|---|---|
| 0.3 | 0.307 / 0.307 | 2.3 / 2.1 | 0.89° / 0.84° | +12 % |
| 0.4 | 0.412 / 0.414 | 2.5 / 2.1 | 0.93° / 1.00° | +18 % |
| 0.5 | 0.505 / 0.511 | 3.3 / 2.3 | 1.43° / 1.51° | **+45 %** |
| **0.6** | **0.493 / 0.553** | 4.8 / 4.9 | 2.67° / 3.79° | −2 % |
| 0.7 | 0.456 / 0.461 | 5.2 / 5.3 | 3.72° / 4.24° | −1 % |

- 저속(0.3~0.5)은 **여전히 횡 진동 악화** (+12 ~ +45 %)
- 0.6 은 roll σ 가 좋아 보이지만 **속도가 0.553 → 0.493 (−11 %)** — 9/16 Q5 의
  "느려져서 조용해진 것"과 같은 모양이다. 개선이 아니다
- **기대가 빗나간 이유**: Q7 §4 에서 확인했듯 보폭을 줄여도 **롤 CoP 마진은 안 늘었다**
  (이득은 착지 품질에서 나왔다). `J̇q̇` 가 요구하던 건 그 마진이었으므로 앞뒤가 맞는다

**판정 불변: `--jdot` 기본 꺼짐.** 재시험 조건을 "보폭 후"에서
**"롤 CoP 포화가 실제로 풀린 뒤"** 로 고친다 (`Fz,min` 램프·`sf(v)` 이후 다시 볼 것).

## Q7. 보폭 식을 적용해보자 — **`--sidew 13` 채택**, 그리고 예측 하나 기각

> "보폭 식 적용해서 시작해보자. 테스트해보고 괜찮으면 여기서 확장."
> 계획(요약 §5)대로 ① 고정값으로 감 보기 → ② 속도 함수 순서로 진행.

### 1. 구현 ([09_walk.py](../MPC/src/09_walk.py))

`side_offset` 의 y(±11.8 cm)는 G1 `stand` 키프레임에서 물려받은 값이었다 (9/18).
기하값은 `_side_geom` 으로 보존하고 그 위에 **보폭 정책**을 얹었다:

```
--sidew <cm>    고정 보폭           side_offset[1] = ±w/2
--sidew auto    w(v) = 19.33 − 4.33·v_ramped [cm], [14, 20] 클램프   (배포 RL 회귀)
(없음)          기하 기본 23.7 cm — 어제와 동일
```

바뀐 호출은 `raibert_target(..., self.side_offset_at(t)[i], ...)` 한 줄.
측정 스크립트: [13_sidew_ab.py](../MPC/src/13_sidew_ab.py).

### 2. 결과 — 120 초 전 항목 통과, **좁을수록 낫다 (13 까지)**

### 3. ★ 왜 좋아지나 — 기전 실측 (기하 vs 13 cm, 몸 yaw frame)

| vx | 보폭 | `Fy` RMS | `v_y` RMS | **착지 목표 횡 쓸림** | 롤 CoP | 피치 CoP | mz 폭 |
|---|---|---|---|---|---|---|---|
| 0.5 | 기하 | 39.7 N | 0.099 | **7.9 cm** | 0.73 | 0.62 | 14.9 |
| 0.5 | 13.0 | **16.8 N** | **0.026** | **1.8 cm** | 0.77 | 0.52 | 17.6 |
| 0.6 | 기하 | 40.9 N | 0.113 | 8.8 cm | 0.84 | 0.67 | 10.1 |
| 0.6 | 13.0 | **20.4 N** | **0.069** | **2.6 cm** | 0.80 | 0.67 | 10.2 |

횡 LIP 는 `ÿ = ω₀²(y − p)` — 발이 옆으로 멀수록(`|y−p|` ∝ 보폭) 횡 가속이 크다.
보폭을 절반으로 줄이니 **횡력 수요가 절반**(40 → 17 N), **횡 속도 요동이 −74 %**,
그래서 capture 항 `v_y/ω₀` 이 **착지 목표를 쓸어내는 폭이 7.9 → 1.8 cm (−77 %)**.
스윙 발이 **거의 고정된 과녁**을 쫓게 된 것.

> **9/16 §4 와 짝을 이루는 결과다.** 그때 `td_mode` lp/fz 로 목표 쓸림을 **억제**했더니
> 0.5 가 13 초에 붕괴했다 (쓸림이 횡 안정화를 받치고 있었으므로).
> 이번엔 쓸림의 **원인(v_y 요동) 자체를 줄였고** 보정 능력은 그대로다.
> 당시 결론 *"보정을 억제하지 말고 보정의 필요를 줄여라"* 가 그대로 실현됐다.

### 4. ⚠ 기각된 예측 — "보폭↓ → 횡 CoP↓"

요약 §5·§6 에 **검증 가능한 예측**으로 걸어둔 것. 결과:

| vx | 공칭 | 롤 CoP 실측 (접촉력) | 롤 CoP 명령 (QP) | >0.9 |
|---|---|---|---|---|
| 0.5 | 기하 | 0.89 | 0.73 | 28 % |
| 0.5 | 13.0 | 0.96 | 0.77 | 28 % |
| 0.6 | 기하 | 0.98 | 0.83 | 45 % |
| 0.6 | 13.0 | 1.03 | 0.80 | 49 % |

**명령 측은 평평, 실측은 소폭 상승.** 롤 CoP 여유는 안 생겼다.
배포 RL 의 상관 +0.951 은 **속도를 가로지른** 상관이었지 한 속도 안의 인과가 아니었다.
이득은 **CoP 마진이 아니라 착지 품질(§3)** 에서 나왔다.
mz 허용 폭도 0.5 에서만 소폭 개선(14.9 → 17.6, 폐쇄 6 → 0 %), 0.6 은 불변.

**덤으로 잡은 계측 버그**: 명령 측 롤 CoP 를 월드 frame `mx` 로 계산하고 있었다.
제약은 몸 yaw frame 에서 걸리는데 `my`(±30 N·m) ≫ 롤 예산(8 N·m)이라 yaw 5° 만으로
예산의 32 % 가 새어든다. 9/18 Q4 표의 평균(0.75)은 유효, **">0.9 비율 50 %" 는 28 % 가 맞다**
(그 표에 정정 주석 추가).

### 5. `auto`(속도 함수)는 보류

RL 회귀식은 0.5 m/s 에서 17.2 cm 를 주는데 **우리 최적은 13 cm** 로 더 좁고,
0.3~0.6 범위에서 **속도 의존성이 안 보인다** (전 속도에서 13 이 최선).
0.7 에서만 15 가 13 을 근소하게 앞선다 (0.470 vs 0.456).
→ **RL 에서 빌릴 건 방향이지 값이 아니다.** `--sidew 13` 고정을 권장 구성에 편입,
`auto` 는 플래그로 보존 (고속 영역을 열게 되면 계수를 우리 데이터로 다시 맞출 것).
