## Q1. MPC 는 GRF 만 구하는데 거기서 토크는 어떻게 나오나? PD 게인은 어디에 쓰이나?

> MATLAB 에서는 GRF(접촉력)까지만 구했음. 그 다음이 통째로 빈칸.

### 0. 큰 그림 — 빈칸은 딱 한 줄짜리 수식이다

```
MPC (100 Hz)                     토크 사상 (500 Hz)              MuJoCo
  상태 x(13) ─→ QP ─→ W(12)  ──→  τ = qfrc_bias − JᵀW  ──→  d.ctrl[:] = τ
                    발에 걸릴            ↑                        모터가 그 토크를 냄
                    wrench           야코비안 전치                 → 실제 접촉력 발생
```

빈칸의 정체는 **Jᵀ (야코비안 전치)** 하나다. MATLAB 에서 멈춘 지점부터 모터까지는
사실상 이 한 줄이고, 나머지는 "SRB 가 모르는 것"을 메우는 보조 항들이다.

우리 코드에서 그 한 줄: [09_walk.py:259](../MPC/src/baseline/09_walk.py#L259), [09_walk.py:305](../MPC/src/baseline/09_walk.py#L305)

### 1. 핵심 — 왜 하필 야코비안의 '전치'인가 (가상일 원리)

다리 하나를 보자. 관절각 q(6개) 가 정해지면 발 위치 p(3D) 가 정해진다: `p = f(q)`.
이걸 미분한 게 야코비안이다:

```
ṗ = J q̇          J = ∂p/∂q  (3 × 6)     ← 속도 관계 (순방향 운동학의 미분)
```

여기서 **에너지(일률)는 어느 좌표계에서 계산하든 같아야 한다**는 물리 법칙을 쓴다.

```
발에서 본 일률   = F · ṗ  = F · (J q̇) = (JᵀF) · q̇
관절에서 본 일률 = τ · q̇
```

임의의 q̇ 에 대해 두 값이 같으려면:

```
        τ = Jᵀ F            ← 이게 전부다
```

**중요**: 이건 근사가 아니라 **항등식**이다. SRB 근사, 선형화, 이산화 같은 건
W 를 *계산*하는 쪽(MPC)의 이야기고, W 를 토크로 *옮기는* 이 단계는 정확하다.
(그래서 검증할 때 "부호와 크기가 맞나"만 보면 됐다 — Step 1, `03_grf_to_tau.py`)

**wrench(힘 3 + 모멘트 3)로 확장**하면 회전 야코비안이 붙는다:

```
τ = J_pᵀ F + J_rᵀ m       J_p = mj_jacSite 의 jacp,  J_r = jacr
```

MuJoCo 가 `mujoco.mj_jacSite(m, d, jacp, jacr, sid)` 로 둘 다 한 번에 준다
([09_walk.py:257](../MPC/src/baseline/09_walk.py#L257)).

> **왜 '전치'이지 '역행렬'이 아닌가**: 역행렬 J⁻¹ 은 *운동학* 문제(발을 여기로
> 보내려면 관절을 얼마나?)의 답이고, 전치 Jᵀ 는 *정역학* 문제(발에 이 힘을 주려면
> 관절 토크는?)의 답이다. 힘 제어를 하면 IK(역기구학)도, 행렬 역변환도 필요 없다 —
> 특이자세에서 J⁻¹ 은 폭발하지만 Jᵀ 는 멀쩡하다는 실용적 장점까지 따라온다.
> (특이자세 얘기는 README 의 랩장 피드백 Q&A 참고)

### 2. 부호 — 왜 `−JᵀW` 인가 (마이너스가 붙는 이유)

MuJoCo(그리고 일반 다물체) 운동방정식:

```
M(q) q̈ + qfrc_bias(q,q̇) = τ + Jᵀ f_외력
```

여기서 **접촉력(GRF)은 '외력'** 이다 — 땅이 발을 밀어주는 힘이니까. 즉 GRF 는
이미 `+Jᵀ W` 라는 일반화 힘으로 방정식에 들어와 있다.

stance 다리가 해야 할 일은 **강체 기둥처럼 형태를 유지**하는 것 (q̈_다리 = 0).
그러려면 모터가 그 일반화 힘을 정확히 상쇄해야 한다:

```
0 + qfrc_bias = τ + Jᵀ W      →      τ = qfrc_bias − Jᵀ W
```

**직관**: 땅이 발을 위로 밀면, 그 힘은 다리를 **접으려고(buckling)** 한다.
무릎이 꺾이고 엉덩이가 주저앉는 방향. 모터는 정확히 그만큼 **펴는 쪽**으로 버텨야
하고, 그게 마이너스 부호의 의미다. 로봇은 "밀어서" 일어서는 게 아니라
"접히지 않게 버텨서" 서 있다.

> 우리 프로젝트의 부호 사고들: MPC_NOTES 6절. 부호 하나 틀리면 로봇이 즉시 주저앉거나
> 튕겨 나가서, 증상만으로는 원인을 못 찾는다 — `05_sign_check.py` 를 따로 만든 이유.

### 3. `qfrc_bias` — SRB 가 모르는 것을 메우는 항

`τ = qfrc_bias − JᵀW` 의 앞항. MuJoCo 가 계산해주는 **중력 + 코리올리/원심력**의
관절공간 값이다 (전신 모델 기준, 다리 12링크 + 팔 + 몸통 전부 포함).

왜 필요한가: MPC 의 SRB 모델은 로봇을 **강체 하나**로 본다 — 다리 링크 각각의
무게를 모른다. 그래서 순수하게 `τ = −JᵀW` 만 주면 **서지도 못한다**. 실측:
무릎에서 4.6 N·m 차이, 힙 피치는 **부호까지 반대**였다 (PHYSICS_MAP 2절).

- `τ = qfrc_bias` 만 주고 접촉이 없으면 → 로봇이 공중에 그대로 떠 있다 (중력 상쇄)
- 거기에 `−JᵀW` 를 더하면 → 계획한 접촉력이 정확히 발생한다

**부수 효과 (21절에서 발견)**: qfrc_bias 를 더하기 때문에 지면에 실제로 나타나는
접촉력이 **정확히 W** 가 된다 (다리 자체 무게는 모터가 따로 감당). 그래서 "상체만
SRB" 실험에서 유효 중력이 `g·M_tot/M_ub` 여야 했던 것 — 다리 무게가 전부 W 에
매달린다. reference 는 bias 를 안 넣어서 접촉력이 W+다리무게로 자기증강된다.
**같은 "상체 SRB"라도 토크 사상이 다르면 모델이 달라진다.**

### 5. PD 게인 — 두 종류가 있고, 쓰임이 다르다

#### (a) 관절공간 PD — "이 관절을 이 각도로 잡아라"

```python
tau[a] += kp_up * (q_ref[관절] − q[관절]) − kd_up * q̇[관절]
```
[09_walk.py:310](../MPC/src/baseline/09_walk.py#L310). 가장 단순한 형태 — 서보모터가 하는 일 그대로.
야코비안이 **필요 없다** (관절 각도를 직접 명령하니까).

- 단위: kp [N·m/rad], kd [N·m·s/rad]
- 우리 값: kp_up = 60 (기본) 또는 **300** (`--uppd 300`, 권장 구성), kd = kp/15
- 역할: 허리·팔을 굳혀서 로봇을 **SRB 가정에 가깝게** 만든다. 상체가 흐물거리면
  다리 반작용에 휘둘려 MPC 의 강체 가정이 깨진다 (Step5 디버깅 2차).
- `--uppd 300` 이 0.3 m/s 완주의 필수 조건인 이유가 이것.

#### (b) 작업공간(Cartesian) PD — "발을 이 지점에 놔라"

```python
F   = kp * (p_des − p_foot) + kd * (v_des − v_foot)     # gait.py:180
mom = kp_ori * axis − kd_ori * ω_foot                   # gait.py:193 (발바닥 수평)
τ  += jacp.T @ F + jacr.T @ mom                         # 09_walk.py:289
```

**개념**: 실제 발과 목표 발 사이에 보이지 않는 **스프링+댐퍼를 매단다**.
그 가상의 힘을 계산한 뒤 `Jᵀ` 로 관절 토크로 번역한다. 그래서 "임피던스 제어".

- 단위: kp [N/m] ← **강성**, kd [N·s/m] ← 감쇠. (관절 PD 와 단위가 다르다!)
- 우리 값: kp = 2500 N/m, kd = 80 ([gait.py:127](../MPC/src/baseline/gait.py#L127))
  → 발이 1 cm 어긋나면 25 N 의 복원력
- **IK 가 필요 없다**: 궤적을 월드 좌표로 그리고(발이 아치를 그리며 착지점으로),
  오차를 월드에서 재고, Jᵀ 로 옮긴다. 관절 목표각을 뽑는 역기구학 단계가 통째로 없음.

**게인 크기의 의미 = 대역폭**:
```
ω_n ≈ √(kp / m_유효)   — 다리 유효질량 ~5 kg, kp=2500 → ω_n ≈ 22 rad/s ≈ 3.5 Hz
```
swing 시간이 0.2 s(=5 Hz) 인데 추종 대역폭이 3.5 Hz 면 아슬아슬하다. 실제로
초기값 kp=350(1.3 Hz)에서는 **발이 궤적을 못 쫓아 착지가 한 박자 늦고**, "스케줄상
stance 인데 발은 공중" 갭이 매 스텝 roll 킥을 만들어 발산했다 (Step5 디버깅 1차).
→ 2500 으로 올려서 해결.

> reference 는 이 게인을 상수로 두지 않고 `kp = ω_n²·Λ(q)` 로 **자세마다 재계산**해서
> 대역폭을 100 rad/s 로 **일정하게** 유지한다 (Λ = 겉보기 관성). 우리 미적용 후보 #6.

### 6. ★ stance 다리에는 왜 PD 가 없는가 (가장 헷갈리는 지점)

①번 채널을 다시 보면 **피드백 항이 없다**. 발 위치 오차를 재지도 않는다.
"다리를 제어 안 하는 것 아닌가?" 싶지만, 피드백은 **한 층 위에서** 일어난다:

```
       [100 Hz]  측정 x → MPC 재풀이 → 새 W        ← 피드백은 여기
       [500 Hz]  τ = qfrc_bias − JᵀW               ← 여기는 순수 전달
```

로봇이 앞으로 기울면 → 다음 MPC 가 그 x 를 보고 → 자세를 되세우는 W 를 새로 계획.
즉 **MPC 자체가 거대한 상태 피드백 제어기**다 (예측 지평까지 갖춘).

이게 힘 제어 기반 보행의 핵심 철학이다:
- 위치 제어라면 "발을 여기 놔라"로 명령하고 PD 가 오차를 잡는다 → 지면이 예상과
  다르면 발이 땅을 뚫거나 허공을 짚는다 (강성 충돌).
- 힘 제어는 "이만큼의 힘으로 밀어라"로 명령한다 → 지면 높이가 달라도 힘은 연속,
  접촉이 부드럽다. 대신 **자세 안정은 상위 루프(MPC)의 책임**이 된다.

500 Hz 에서 아무 일도 안 하는 건 아니다: 같은 W 라도 **q 가 변하면 J 가 변하므로
τ 가 매 스텝 달라진다**. 기하학적 보정이 500 Hz 로 들어가는 셈. (W 는 MPC 사이에
영차 유지 = zero-order hold)

### 8. 마지막 단계 — MuJoCo 에 실제로 넘기는 것

```python
d.ctrl[:] = ctl.torque(d, t)      # 09_walk.py:380
mujoco.mj_step(m, d)
```

`d.ctrl` 이 곧 **모터 토크 [N·m]** 다. 원래 Menagerie G1 모델은 `<position>`
액추에이터(ctrl = 목표 각도)라서, `g1_model.to_torque_actuators()` 로 gain/bias 를
바꿔 **motor(직접 토크)** 로 만들어 뒀다 ([g1_model.py](../MPC/src/baseline/g1_model.py)).

그리고 `mj_step` 안에서 물리엔진이:
1. τ 를 받아 다리를 버티게 하고
2. 발이 지면을 파고들려 하면 **접촉 제약을 풀어 실제 접촉력을 만들고**
3. 그 접촉력이 몸을 밀어올린다

즉 **우리는 접촉력을 직접 만들지 않는다.** 접촉력이 W 가 되도록 관절 토크를 걸면,
물리엔진(실제 로봇이면 지면)이 그 결과로 W 를 만들어 준다. MPC 의 계획이 물리
법칙을 통해 실현되는 것이고, 그래서 **계획이 물리적으로 실현 가능해야** 한다 —
마찰 원뿔·CoP·mz 제약이 QP 안에 반드시 있어야 하는 이유가 여기다.
(18.7 의 "실현 불가 계획에 기대고 있었다"가 정확히 이 이야기)

## Q2. 몸통이 가만히 있도록 설정하면 안 되나? 왜 계속 앞뒤로 흔들리나?

> 시뮬 영상에서 몸통이 계속 앞뒤(pitch)로 흔들리는 게 보임.

### 0. 먼저 로그로 확인한 사실 (추측 전에 측정)

`logs/` 의 pitch 신호를 FFT + CoP 제약 활성도 분석 (5~25 s 구간):

| 시험 | pitch 진폭 | **지배 주파수** | CoP(피치 권한) 포화 비율 |
|---|---|---|---|
| 제자리 스텝 | ±1.73° | **2.50 Hz** | 0.0 % |
| 직진 0.15 | ±6.30° | **2.50 Hz** | 0.8 % |
| 직진 0.30 | ±12.38° | **2.50 Hz** | **19.4 %** (뒤꿈치쪽 18.3 %) |

**2.50 Hz = 2 / T_gait = 2 / 0.8 s = 발 교대 주파수와 정확히 일치.**
상위 피크 3개도 전부 2.45~2.55 Hz 에 몰려 있다 — 다른 성분이 없다.

→ 이건 **제어 불안정도, 공진도 아니다.** 보행 리듬에 **완전히 동기된 강제 진동**이다.
진폭만 속도에 비례해 커진다 (±1.7 → ±6.3 → ±12.4°).

발 움직이는거 땜에 몸 흔들림 발생한다

### 1. 근본 이유 — 몸통 자세는 '명령'할 수 있는 양이 아니다 (부족구동)

G1 의 모터 23개는 전부 **링크와 링크 사이**에 있다. **월드와 골반 사이에는 모터가 없다.**
로봇은 floating base — 공중에 떠 있는 기준틀이고, 그 자세는 **결과**지 명령이 아니다.

> 혼동하기 쉬운 지점: `--uppd 300` (상체 PD) 은 **골반에 대한 상체**를 굳히는 것이지
> **월드에 대한 골반**을 잡는 게 아니다. 상체 PD 를 아무리 세게 해도 골반이 통째로
> 앞뒤로 도는 건 못 막는다 (오히려 몸 전체가 한 덩어리로 같이 흔들릴 뿐).

몸통 자세를 바꾸는 유일한 수단은 **발이 땅에서 받는 wrench** 뿐이다. 그래서
"몸통을 고정한다"는 명령은 존재할 수 없고, "몸통이 덜 흔들리도록 지면 wrench 를
계획한다"만 가능하다. 그게 MPC 가 하는 일이다.

### 2. 그 유일한 수단조차 발 크기에 갇혀 있다

피치 모멘트를 만드는 방법은 두 가지뿐이고, 둘 다 대가가 있다:

**(a) 발목 모멘트 (CoP 이동)** — 공짜지만 작다
```
−l_t·Fz ≤ m_ground,y ≤ l_h·Fz     l_t(발가락)=0.12 m, l_h(뒤꿈치)=0.05 m
ΣFz ≈ 322 N 일 때  →  [−39, +16] N·m
```
**비대칭이 심하다**: 뒤꿈치가 5 cm 뿐이라 **뒤로 미는 권한이 앞의 2.4배 약하다.**
0.3 m/s 에서 포화가 전부 뒤꿈치쪽(18.3 %)에 몰린 이유가 이것.

**(b) 수평력 Fx × CoM 높이** — 크지만(μ 한계에서 ~146 N·m) **몸을 움직여 버린다**
피치를 세우려고 Fx 를 쓰면 로봇이 앞뒤로 가속된다. 자세와 위치를 **하나의 힘으로
독립 제어할 수 없다** — 역진자의 숙명(부족구동)이다.

그래서 MPC 는 (a) 를 먼저 다 쓰고, 모자라면 (b) 로 넘어가며 **위치 오차를 대가로
지불**한다. 0.3 m/s 에서 CoP 가 19 % 포화라는 건 **(a) 가 바닥났다**는 뜻 —
그 지점부터는 튜닝 문제가 아니라 권한 문제다.

추가로 우리 gait 는 **단일지지가 50 %** (T=0.8, stance 75 %, offsets 0/0.5).
그 구간엔 발 하나의 CoP 만 쓸 수 있다.

### 3. 교란은 매 스텝 확실하게 들어온다 — 다리 반작용

2.50 Hz 라는 측정값이 범인을 지목한다. 0.2 s 짜리 swing 마다:

- 다리 한쪽 **7.19 kg** (양다리 43.1 %) 이 앞으로 나갔다가 감속한다
- 작용-반작용: 몸통은 뒤로 밀렸다가 앞으로 당겨진다 (**앞뒤 흔들림**)
- 발이 좌/우 교대하므로 주기는 T/2 = 0.4 s = **2.5 Hz** ✓
- 속도가 빠를수록 보폭·가속도가 커져 반작용도 커진다 → **진폭이 속도에 비례** ✓

즉 흔들림은 "제어가 서툴러서"가 아니라 **걷는다는 행위 자체의 반작용**이다.
(사람도 걸을 때 몸통이 스텝 주파수로 흔들린다 — 문제는 존재 여부가 아니라 크기)

### 4. 그런데 MPC 는 이 교란을 '모른다' — SRB 근사

MPC 의 모델은 **강체 하나**다. 다리가 없다. 그래서
**"0.1 초 뒤 내 다리가 앞으로 나가며 몸통을 뒤로 밀 것"을 예측할 수 없다.**

- 예측 못 함 → 미리 상쇄 못 함 → **오차가 생긴 뒤에야 반응**
- 주기 교란에 반응만 하는 제어기는 **항상 위상이 뒤처진** 잔류 진동을 남긴다
- 100 Hz 로 다시 풀어도 마찬가지 — 빠르게 반응할 뿐, 예측하는 게 아니다

이게 `--swingid`(τ += M q̈_swing,des) 가 존재하는 이유다: 계획된 swing 가속을
**역동역학으로 미리 감당**해서 "모델이 모르는 교란"을 부분적으로 "아는 것"으로
바꾼다. 부분적인 이유는 J̇q̇ 항을 생략했고, MPC 자체에는 여전히 안 들어가기 때문.

여기서 **residual RL 의 자리**가 생긴다: 모델 기반으로 메울 수 있는 건 먼저 메우고
(feedforward), 그래도 남는 이 반작용이 학습이 메울 gap 이다. (MPC_NOTES 17.4)

### 5. 가중치도 pitch 를 일부러 양보하게 되어 있다

```
Q = [roll 10, pitch 10, yaw 20 | px 50, py 50, pz 300 | ω 5,5,5 | v 20,20,50 | g 0]
```
pitch 가중치 10 vs 높이 300 — **30배 차이**. MPC 한테 "자세보다 위치가 30배 중요"
라고 말해둔 것이다. 의도적이다: 한정된 CoP 권한을 자세에 쓰면 위치가 밀리고,
**넘어지는 건 위치 오차 쪽**이라서. pitch 가중치를 올리면 흔들림은 줄지만 더 빨리
넘어진다 (13절 튜닝 민감도와 같은 맥락).

### 6. 정리 — 왜 "고정"이 안 되나

| 층위 | 이유 |
|---|---|
| 구동 | 월드-골반 사이에 모터가 없다 (부족구동) — 자세는 결과지 명령이 아님 |
| 권한 | 유일한 수단인 발목 모멘트가 발 크기에 갇힘 (뒤꿈치 5 cm → 16 N·m). 0.3 에서 19 % 포화 |
| 결합 | 더 큰 수단(Fx)은 자세와 위치를 분리 못 함 — 역진자 |
| 예측 | SRB 모델이 다리를 몰라서 교란을 예측 못 하고 반응만 함 (위상 지연) |
| 의도 | 가중치가 pitch(10)보다 위치(300)를 우선하도록 설정됨 |

### 7. 그럼 무엇을 할 수 있나 (다음 작업 후보)

**교란 자체를 줄이기** ← 가장 효과적
- 착지 수직속도 0 (스윙 z 를 2단 smoothstep 으로) — 착지 충격 제거
- 착지 wrench 램프 0.02 s — 힘의 계단을 경사로 (reference 방식)
- 스윙 추종 대역폭 ↑ (kp = ω_n²·Λ(q) 자세별 스케줄링) — 계획대로 움직이면 반작용도 계획대로

**교란을 미리 알려주기**
- `--swingid` 정밀화 (J̇q̇ 포함), 또는 swing 반작용을 MPC 에 known disturbance 로 주입

**권한 늘리기**
- gait 타이밍 (이중지지 비율 ↑, 주기 조정), 팔 스윙으로 각운동량 상쇄 (사람이 하는 것)
- 발을 크게 = 하드웨어 변경 (근본적이지만 우리 범위 밖)

> **주의**: 흔들림을 0 으로 만드는 게 목표가 아니다. 120 초 실험에서 직진 0.3 이
> 30 초에 무너진 건 **횡(roll) 모드**였고 (MPC_NOTES 22절), pitch 흔들림은 그와
> 별개다. 다만 위 대책들(착지 충격 제거)은 두 모드 모두에 동시에 듣는다.

## Q3. reference 는 흔들림을 어떻게 잡았나? 가중치·PD 게인 참고

> 어느 정도 되는 코드(전진 0.6 m/s, 회전 1.3 rad/s)를 참고하고 싶음.

**결론 먼저**: 가중치보다 **궤적과 게인 쪽에서 훨씬 큰 차이**가 나왔다. 특히
**우리는 발을 지면에 초속 0.785 m/s 로 내리꽂으라고 명령하고 있다** (reference 는 0).
흔들림의 직접 원인으로 이만한 게 없다.

> ⚠ 먼저 알아둘 것: reference README 는 **MIT humanoid 만 검증된 타깃**이고
> G1/H1 설정은 "validated defaults 가 아니라 robot-specific tuning targets"라고
> 명시한다. 그래서 아래에서 **MIT 값을 주 근거로, G1 값은 참고로** 본다.

### 1. ★ 착지 수직속도 — 가장 큰 발견 (즉시 고칠 수 있음)

우리 스윙 z 궤적 ([gait.py:150](../MPC/src/baseline/gait.py#L150)):
```python
p_des[2] += h_swing * sin(πs)                    # 아치를 더함
v_des[2] += h_swing * π * cos(πs) / T_swing      # s=1 에서 cos(π) = −1
```
→ **착지 순간(s=1) 명령 수직속도 = 0.05 × π × (−1) / 0.2 = −0.785 m/s**

reference 는 z 를 **2단 smoothstep**으로 만든다 (올라가서 zMid, 내려와서 목표):
```
s ≤ 0.5:  u=2s,    z: p_init → zMid
s > 0.5:  u=2s−1,  z: zMid → p_final,   v_z = blendZDot(u)·… ,  blendZDot(1) = 0
```
→ **착지 수직속도 = 정확히 0** (smoothstep 은 양 끝 미분이 0)

우리는 발을 땅에 **찍고**, reference 는 **내려놓는다.** 매 스텝 0.785 m/s 짜리
충격이 2.5 Hz 로 들어오는 것 — 이게 우리가 Q2 에서 본 2.50 Hz 흔들림의 강제항이다.
게다가 이 충격은 pitch 뿐 아니라 roll 로도 들어가므로, 120 초 실험에서 0.3 을
무너뜨린 **횡 모드**(MPC_NOTES 22절)와도 직결된다.

우선은 배지어 커브로 안하고 사인으로 진행 근데 사인해도 괜찮을거 같다 생각듬

### 2. ★ 스윙 강성 — 수직으로 41배 차이 (실측)

reference 는 kp 를 상수로 두지 않고 **겉보기 관성으로 스케줄링**한다:
```
Λ(q) = (J M⁻¹ Jᵀ)⁻¹        (발끝에서 본 등가 질량)
kp   = ω_n² · diag(Λ)       ω_n 고정 → 자세가 변해도 대역폭 일정
```

우리 G1 crouch 자세에서 실제로 계산한 값:

| | Λ [kg] | reference kp (ω_n=100) | 우리 kp | 우리 등가 ω_n |
|---|---|---|---|---|
| x (전후) | 2.12 | 21,197 N/m | 2500 | 34.3 rad/s |
| y (좌우) | 1.41 | 14,130 N/m | 2500 | 42.1 rad/s |
| **z (수직)** | **10.27** | **102,685 N/m** | **2500** | **15.6 rad/s** |

**수직이 41배 차이.** 다리를 수직으로 움직이려면 거의 편 자세라 등가 질량이 10 kg 나
되는데, 우리는 x·y·z 에 똑같이 2500 을 쓴다. 그 결과 수직 추종 대역폭이
**15.6 rad/s = 2.5 Hz** — swing 이 0.2 s(5 Hz) 짜리 사건인데 대역폭이 그 절반이다.

**실측 증거 (로그)**: 명령 swing 높이 5.0 cm 인데 실제 도달은
**제자리 2.4 cm (48 %), 직진 0.15 에서 3.9 cm (78 %)**. 발이 궤적을 못 쫓고 있다.
→ 발이 계획보다 낮게, 늦게 움직이고, 착지도 계획된 지점·시각과 어긋난다.

(MIT 설정은 ω_n 이 더 높다: `natural_frequency: [151, 151, 110]`)

### 3. gait 타이밍 — 스윙이 짧을수록 반작용이 커진다

| | 주기 T | swing | stance | 이중지지 | swing 높이 | 착지 wrench 램프 |
|---|---|---|---|---|---|---|
| **우리** | 0.8 s | **0.2 s (25 %)** | 0.6 s | **50 %** | 0.05 m | **없음** |
| ref (G1) | 0.7 s | 0.3 s (43 %) | 0.4 s | 14 % | 0.09 m | 0.02 s |
| ref (MIT) | 0.5 s | 0.17 s (34 %) | 0.33 s | 32 % | 0.06 m | 0.01 s |

smoothstep 의 최대 가속도는 `a_max = 6L/T²` 이므로 **T 가 짧으면 제곱으로 커진다.**
0.3 m/s 에서 보폭 L 을 같다고 놓고 비교하면:

```
우리 (T=0.2, L=0.24 m):  a = 36 m/s²  → 다리 7.19 kg 기준 반작용 ≈ 259 N
ref  (T=0.3, L=0.21 m):  a = 14 m/s²  → 반작용 ≈ 101 N        (2.6배 차이)
```

우리 notes 에 있던 "0.3 m/s 에서 swing 에 ~250 N 필요"가 이 계산과 정확히 맞는다.
**스윙을 느긋하게 하면 반작용이 제곱으로 줄어든다** — 대신 이중지지가 줄어  드는 교환.

### 4. 가중치 — 절대값이 아니라 '비율'을 봐야 한다

세 설정의 Q 를 각자의 pz 로 정규화한 값:

| 비율 | 우리 | ref (G1) | ref (MIT, 검증됨) |
|---|---|---|---|
| py / px (횡 vs 전후 위치) | **1.0** | 14.0 | **5.05** |
| roll / pitch | **1.0** | 1.0 | **5.56** |
| **vx / px (속도 vs 위치)** | **0.40** | 0.0033 | **0.0005** |
| ωx / roll (각속도 vs 자세) | **0.50** | 0.011 | 0.0002 |
| R / Q_pz (입력 페널티) | 3.3e-8 | 2e-12 | 9.1e-9 |

읽어야 할 것 세 가지:

**(a) 우리는 속도를 상대적으로 800배 무겁게 본다** (vx/px: 0.40 vs MIT 0.0005).
이게 흔들림과 직접 얽힌다 — 다리 반작용은 2.5 Hz 짜리 **속도 리플**을 만드는데,
속도 가중치가 크면 MPC 가 **그 리플을 쫓아간다.** 쫓으려면 wrench 를 흔들어야 하고,
그게 CoP 권한을 소모하며 진동을 **되먹임**할 수 있다. reference 는 속도를 거의
무시하고 위치만 본다 = 교란을 구조적으로 저역통과시키는 셈.
(단, 우리는 발디딤에 capture point 피드백이 있고 reference 는 없다 — 역할 분담이
다르므로 속도 가중치만 떼어 바꾸면 균형이 깨질 수 있다. 4절 주의사항 참고)

**(b) MIT 는 roll 을 pitch 의 5.6배, 횡 위치를 전후의 5배로 본다.**
우리는 둘 다 1:1. 우리 실패 모드가 **횡/roll 림프사이클**(22절)이었던 걸 생각하면
방향이 맞는 조정이다. G1 설정도 py/px = 14 로 횡 우세.

**(c) 입력 페널티 R 은 MIT 와 우리가 비슷하다** (3.3e-8 vs 9.1e-9, 4배 이내).
reference-G1 의 1e-7 은 극단적으로 자유로운데, 검증 안 된 설정이라 참고만.

## Q4. "발디딤이 순수 피드포워드"가 무슨 뜻인가? capture point 는 Raibert 와 뭐가 다른가?

### 1. 피드포워드 vs 피드백 — 발디딤에서의 의미

- **피드포워드**: 명령·계획만 보고 계산한다. 측정값을 안 본다.
  "0.3 m/s 로 갈 거니까 stance 0.6 s 동안 몸이 18 cm 이동하겠네 → 9 cm 앞에 딛자"
- **피드백**: 측정된 **오차**를 보고 보정한다.
  "명령은 0.3 인데 실제로 0.35 로 가고 있네 → 더 앞에 딛어서 브레이크 걸자"

**우리 식** ([gait.py:91](../MPC/src/baseline/gait.py#L91)):
```
p = hip + v_cmd·(T_st/2)  +  (v − v_cmd)/ω₀  +  k_a·(CoM − anchor)
    └─── 피드포워드 ───┘    └─ 속도 피드백 ─┘   └─ 위치 피드백 ─┘
                              ↑ 측정 v 사용        ↑ 측정 CoM 사용
```

**reference 식** ([SwingFootPlanner.cpp:239-256](../reference/My_Controller/src/SwingFootPlanner.cpp)):
```
target = CoM_측정 + Rz(ψ)·( v_cmd · T_preview )  +  공칭 발 오프셋
         └위치만 측정┘  └────── 전부 명령값 ──────┘
```

**속도 오차 항이 아예 없다.** 코드로 확인: 239행의 `previewVelocity_B` 는
`currentPlanarCommand` = 사용자 명령(필터링된)이지 측정 속도가 아니다. 측정 속도는
`computeStopStanceCenterWorld()` 에서만 쓰이는데, 그건 **명령이 0 일 때(정지)만**
활성화되는 경로다 (`stopCapturePointGain: 0.2`).

> 측정값을 아예 안 쓰는 건 아니다 — 발을 **현재 CoM 기준**으로 놓으므로 위치
> 피드백은 있다. 없는 건 **속도 오차 피드백**이다. 그래서 "속도에 대해 순수 피드포워드".

### 2. 왜 이 차이가 중요한가 — 균형을 누가 잡느냐

발목 권한이 작아서(Q2 참고: roll 은 8 N·m 뿐) **보행 로봇의 주 균형 수단은
"어디에 딛느냐"** 다. 그 수단에 피드백을 넣느냐 마느냐가 전체 설계를 가른다:

| | 발디딤 | 속도 안정 담당 | 그 결과 필요한 것 |
|---|---|---|---|
| **reference** | 피드포워드 | **MPC 가 전담** | 극단적 위치 가중치 (py 100만), 100 Hz 재계획 |
| **우리** | capture 피드백 | MPC + 발디딤 **분담** | 온건한 가중치, 20 Hz 로도 버팀 |

- reference 방식의 장점: 게인 튜닝이 없고, 발 궤적이 리드미컬·예측 가능해진다
  (회전 시 발 yaw 선행 같은 계획을 얹기 쉽다).
- 단점: 외란이 오면 **오직 MPC 만 반응**한다. 그래서 위치 가중치를 극단으로 올리고
  100 Hz 로 돌려야 한다 — 그게 그 패키지의 필연이다.

**그래서 Q3 의 경고가 나온다**: 가중치만 복사하면 **두 루프가 같은 양(횡 속도)을
동시에 제어하게 되어 싸운다.** 우리 검증 리포트 §3 에도 이미 적혀 있다 —
"횡 위치를 MPC(Q_py·sway)와 발디딤(k_pos) 두 루프가 동시에 제어 중, 튜닝 시 둘을
동시에 움직이지 말 것."

### 3. Capture point 란 무엇인가 (LIP 에서 유도)

**선형 역진자(LIP)**: CoM 높이 h 고정, 발 p 에 고정. 수평 동역학은
```
ẍ = ω₀²(x − p),      ω₀ = √(g/h)
```
고유값이 ±ω₀ — **하나가 양수라 불안정**하다 (발 위에서 조금만 벗어나면 지수적으로 넘어짐).

여기서 **발산하는 성분만 뽑아낸다**:
```
ξ = x + ẋ/ω₀                    ← capture point (DCM)
ξ̇ = ω₀(ξ − p)                   ← 대입하면 이렇게 1차식이 됨
```
2차 불안정계가 **1차식**으로 줄었다. 그리고 여기서 바로 읽힌다:

```
p = ξ 로 딛으면  →  ξ̇ = 0  →  발산 멈춤
```
남은 수렴 성분은 e^(−ω₀t) 로 알아서 죽고, CoM 은 발 위로 가라앉는다.

> **즉 capture point = "여기 딛으면 완전히 멈출 수 있는 점"** 이다.
> capture(포획) = 상태를 붙잡아 정지시킨다는 뜻.
> 같은 양을 분야마다 다르게 부른다: capture point(Pratt 2006),
> DCM(divergent component of motion, Takenaka 2009), extrapolated CoM(Hof 2005).

**우리 로봇의 실제 숫자** (crouch 자세):
```
h = z_com − z_ground = 0.672 − 0.035 = 0.637 m
ω₀ = √(9.81/0.637) = 3.92 rad/s
1/ω₀ = 0.255 s        ← 이게 capture 게인
```
→ 1 m/s 로 밀리고 있으면 **25.5 cm 앞**에 딛어야 멈춘다. 직관적으로도 맞는 크기.

### 4. Raibert 와 무엇이 다른가

**Raibert (1986, 호핑 로봇)** — 경험적 휴리스틱:
```
p = v·(T_st/2)  +  k·(v − v_cmd)
    └ neutral point ┘  └ 속도오차 보정 ┘
```
- **neutral point**: stance 동안 몸이 이동할 거리의 **절반**. 여기 딛으면 전반부
  감속과 후반부 가속이 상쇄되어 **순 가감속이 0** — "그대로 유지" 지점.
- 둘째 항의 **k 는 튜닝값**이다. 원 논문 계열에서 0.03~0.5 정도를 쓴다.

**Capture point** — 물리에서 유도:
```
p = x + ẋ/ω₀
```
- 게인 **1/ω₀ = √(h/g)** 가 **모델에서 결정**된다. 튜닝이 아니다.

**형태는 같은데 게인의 출처가 다르다.** 우리 코드는 둘의 혼합이다:
```
p = hip + v_cmd·(T_st/2)   ← Raibert neutral point (단 측정 v 대신 v_cmd)
        + (v − v_cmd)/ω₀   ← Raibert 의 오차 보정 형태 + capture 게인
```

**우리 히스토리가 이 차이를 실측으로 보여준다** (MPC_NOTES 12절, Step5 디버깅 3차):
- k = 0.48 (Raibert 원형) → 과잉 스텝 → 진동이 커지며 **9.5 s 만에 전도**
- 1/ω₀ = 0.255 로 교체 (1.88배 작음) → 해결

속도오차 0.05 m/s 일 때 착지점 이동량: **capture 1.3 cm vs Raibert 2.4 cm.**
발이 2 배 덜 움직인다. 과하게 딛으면 다음 스텝에 반대로 과하게 딛어야 하고,
그게 스텝마다 증폭되는 게 "진동 성장"의 정체였다.

### 5. ⚠ "1/ω₀ 가 정답"은 아니다 (심사 대비)

capture point 는 **"지금 당장 멈추고 싶을 때"**의 답이다. 그런데 주기 보행은
멈추는 게 아니라 계속 걷는 것이고, 매 스텝 발이 바뀐다. 이 경우 **최적
step-to-step 게인은 T_stance 에 의존**한다 (H-LIP / step-to-step 동역학 계열).

정확한 서술: *"순간 capture point 게인 1/ω₀ 가 이 주기(T_st = 0.6 s)에서 경험적으로
최선이었다"* — VERIFY_REPORT §3 의 지적이 이것.

### 6. 정리

| | Raibert | Capture point | 우리 구현 | reference |
|---|---|---|---|---|
| 게인 출처 | 경험적 튜닝 (k) | 물리 (1/ω₀ = √(h/g)) | 1/ω₀ = 0.255 s | 게인 없음 (보행 중) |
| 속도 피드백 | 있음 | 있음 | 있음 | **없음** (정지 시만 0.2) |
| 위치 피드백 | 없음 | — | 있음 (k_a = 0.15, y 표류 방지) | 있음 (측정 CoM 기준) |
| 균형 책임 | 발디딤 | 발디딤 | 발디딤 + MPC 분담 | **MPC 전담** |

## Q5. MPC 를 100 Hz 로 돌리면 residual RL 병렬화에 문제가 되지 않나?

> "reference 는 100 Hz 였는데, 병렬화할 때 Hz 가 너무 크면 문제 아닌가?"
> (+ 이후 확인: 논문들도 100 Hz 를 쓴다)

### 0. 먼저 사실 정정 — 우리는 이미 100 Hz 다

이전 REFERENCE_ANALYSIS 초판에 "우리 20 Hz"라고 적었는데 **오류**였다. 확인:

```
sim timestep 0.002 s (500 Hz),  DECIM = 5  →  MPC 재풀이 = 100 Hz
로그도 120 초에 12000 행 = 100 Hz ✓
```

reference 와 **재풀이 주기는 동일**하다. 실제 차이는 다른 데 있었다:

| | 재풀이 | 지평 이산화 dt | 지평 길이 | 솔버 |
|---|---|---|---|---|
| 우리 | **100 Hz** | 0.05 s | 0.8 s (N=16) | quadprog (dense, warm start 없음) |
| ref G1 (미검증) | 100 Hz | 0.02 s | 0.5 s (N=25) | OSQP (sparse) + shifted warm start |
| **ref MIT (검증됨)** | **50 Hz** | 0.02 s | 0.5 s (N=25) | 〃 |

> 주목: reference 가 **검증했다고 밝힌 MIT 설정은 50 Hz** 다
> (`iterations_between_solve: 10` → 500/10). 100 Hz 는 그들 스스로
> "validated defaults 아님"이라고 적은 G1 설정 쪽이다. 즉 100 Hz 는 상한이지
> 필수 조건이 아니다.

### 1. 실측 — 우리 MPC 주기는 얼마까지 내려가나

직진 0.15 m/s, 120 초 기준 (지평 N·dt 는 고정, **재풀이 주기만** 변경):

| 재풀이 | 결과 | CoM y 진폭 | 비고 |
|---|---|---|---|
| 100 Hz (현행) | ✓ 120 초 | ±4.6 cm | |
| **50 Hz** | ✓ 120 초 | ±4.3 cm | 손실 없음 (오히려 미세 개선) |
| **25 Hz** | ✓ 120 초 | ±4.6 cm | 손실 없음 |
| 20 Hz | ✗ 17.4 초 | — | **절벽** |
| 10 Hz | ✗ 3.2 초 | — | 즉시 붕괴 |

25 Hz 를 다른 태스크로 교차검증: **제자리 120 초 ✓ (±4.2 cm), 회전 0.5 rad/s
120 초 ✓ (오차 −3.9°)** — 100 Hz 결과와 사실상 동일.

**→ 우리 바닥은 25 Hz. 현재 100 Hz 에는 4배의 여유가 은행에 들어 있다.**

절벽이 25→20 Hz 사이(재풀이 간격 40→50 ms)에 있는데, 공교롭게 50 ms 는 우리
`DT_MPC` 와 같다. "첫 계획 스텝이 만료되기 전에 다시 풀어야 한다"는 해석이
그럴듯하지만 — reference MIT 는 재풀이 간격 20 ms = dt_mpc 20 ms 로 **같은데도**
동작한다. 그러니 이건 **가설일 뿐 확인된 기전이 아니다.** 확실한 건 실측된 바닥이 25 Hz 라는 것.

### 2. ★ 진짜 병목은 Hz 가 아니라 '1회 풀이 비용'이다

같은 100 Hz 라도 **누가 푸느냐**가 다르다:

| | 우리 | reference |
|---|---|---|
| 구현 | Python + quadprog (dense active-set) | C++ + OSQP (sparse ADMM) |
| warm start | **없음** | shifted warm start |
| 실측 solve 시간 | 중앙값 **7.6 ms**, p99 60 ms, 최대 **199 ms** | (C++/OSQP 급이면 통상 1 ms 미만) |
| 100 Hz 예산(10 ms) 초과율 | **10.2 %** | — |

**같은 Hz 를 쓰는데 1회 비용이 한 자릿수~두 자릿수 배 차이 난다.**
병렬화에서 터지는 건 Hz 가 아니라 이 부분이다.

### 3. 처리량 실측 — residual RL 예산은 되나

20 초 시뮬 실행에 걸린 실제 벽시계 시간 (단일 환경):

```
100 Hz MPC:  26.2 초  →  실시간 대비 0.76x
 25 Hz MPC:  11.4 초  →  실시간 대비 1.75x   (2.3배 빠름)
```

residual RL 을 5 M policy step (50 Hz 정책 = 시뮬 100,000 초) 으로 가정하면:

| 구성 | 단일 프로세스 | 16 프로세스 | 32 프로세스 |
|---|---|---|---|
| 100 Hz MPC | 36.6 시간 | **2.3 시간** | 1.1 시간 |
| 25 Hz MPC | 15.9 시간 | **1.0 시간** | 0.5 시간 |

**결론: CPU 멀티프로세스(16~32 env) 규모라면 100 Hz 그대로도 충분히 돌아간다.**
residual RL 은 밑바닥부터 배우는 게 아니라 **이미 되는 컨트롤러 위의 보정**을
배우는 것이라 표본 요구량이 훨씬 적다 — 이 규모가 현실적이다.

### 4. 언제 문제가 되나 — GPU 규모로 갈 때

1000+ 환경(MJX/Isaac 스타일 GPU 병렬)을 원하면 얘기가 달라진다:

- 우리 QP 는 scipy/quadprog = **CPU 전용, 배치 불가**. 환경마다 순차 호출.
- 해결하려면 QP 를 **배치 가능한 형태로 재구현**해야 한다 (JAX/PyTorch 에서
  고정 반복수 ADMM 등). 모든 환경이 **구조가 동일하고 데이터만 다르므로**
  배치에는 이상적이지만, 구현 비용이 크다.
- 학부논문 범위에서는 **권장하지 않는다.** CPU 16~32 프로세스로 충분.

### 5. 비용을 줄여야 할 때의 카드 (효과 순)

| 카드 | 예상 효과 | 비용/리스크 |
|---|---|---|
| 재풀이 25~50 Hz 로 | 2.3배 처리량, **실측상 성능 손실 없음** | 낮음 (검증 완료) |
| 지평 N 16 → 10 (0.5 s, reference 와 동일) | dense QP 는 O(N³) → 이론상 ~4배 | 중간 (회귀 필요) |
| OSQP + warm start 로 교체 | 연속 풀이가 유사하므로 큰 이득 | 중간 (sparse 정식화 필요) |
| 배치 QP (JAX) | GPU 규모 개방 | **높음** |

### 6. 실험 설계상 주의 (논문용)

1. **baseline 과 residual RL 을 반드시 같은 MPC 주기로 비교할 것.**
   MPC 를 느리게 하면 baseline 이 나빠지고 → RL 기여가 커 보인다. 의도치 않은
   자기기만이 되기 쉽다.
2. 한편 **개념적으로는** 느린 MPC + 빠른 정책이 깔끔한 분업이다:
   Q1 6절에서 봤듯 **stance 다리의 유일한 피드백이 MPC 재풀이**인데, 그 자리를
   고속 정책이 메우는 구조가 된다 ("MPC = 느린 구조적 사전계획, RL = 빠른 반응 보정").
   다만 이건 **설계 선택으로 명시**해야지, 비용 절감의 부산물로 슬쩍 넣으면 안 된다.
3. 지금 측정값(25 Hz 까지 손실 없음)은 **여유가 있다는 뜻이지 낮추라는 뜻이 아니다.**
   기본은 100 Hz 유지, 병렬 규모가 모자랄 때 꺼내 쓸 카드로 보관.

## Q6. Residual MPC 논문(Jeon et al., T-RO 2026) 기준으로 MPC 주기는 몇 Hz 가 적당한가?

> 우리가 구현 목표로 삼은 논문: "Residual MPC: Blending RL with GPU-Parallelized MPC"
> (Se Hwan Jeon, Ho Jae Lee, Seungwoo Hong, Sangbae Kim / MIT + 고려대)

### 0. 결론 — **100 Hz 로 간다.** 단, 이유가 중요하다

논문은 **우리가 궁금해한 바로 그 절단 실험(25 Hz)을 이미 했다** (Fig. 7):

| 학습 곡선 (4.5e7 samples) | 최종 보상 |
|---|---|
| Residual, **100 Hz** | **~12.5** (가장 빠르게 수렴) |
| End-to-End RL | ~12.5 (느리게 도달) |
| MPC only, 100 Hz | ~8.5 (고정, 학습 없음) |
| **Residual, 25 Hz** | **~7** ← MPC 단독보다도 낮다 |

논문 원문: *"when the MPC controller is **not stable closed-loop**, it significantly
detriments the training - the initialized control prior is no longer a reliable
signal, and the policy requires far more samples to converge."*

**★ 여기서 정확히 읽어야 할 것**: 문제의 원인은 "25 Hz 라는 숫자"가 아니라
**"그 주기에서 MPC 가 닫힌루프 안정하지 않다"** 는 것이다. residual 구조는 MPC 를
**warm start / prior** 로 쓰는데, prior 가 무너지면 그 위에 얹는 학습도 무너진다.
즉 판단 기준은 주기가 아니라 **"이 주기에서 내 MPC 가 멀쩡한가"** 다.

### 1. 그 기준을 우리 컨트롤러에 적용하면 (실측, Q5)

우리 MPC 는 **25 Hz 에서도 닫힌루프 안정했다**:

| 재풀이 | 직진 0.15 (120 s) | 제자리 (120 s) | 회전 0.5 (120 s) |
|---|---|---|---|
| 100 Hz | ✓ ±4.6 cm | ✓ | ✓ |
| 50 Hz | ✓ ±4.3 cm | — | — |
| **25 Hz** | **✓ ±4.6 cm** | **✓ ±4.2 cm** | **✓ −3.9°** |
| 20 Hz | ✗ 17.4 s | — | — |

논문의 MPC 는 25 Hz 에서 불안정한데 우리 건 안정하다. 모순이 아니라 **조건이 다르다**:

| | 논문 MPC | 우리 MPC |
|---|---|---|
| 모델 | **kinodynamic 24 DoF** (q, q̇, F 전부 최적화) | SRB 13-state (훨씬 단순) |
| 이중지지 | **없음** (φ=0.5 에서 전환, offset 0.5 → 항상 단일지지) | **50 %** — 훨씬 관대 |
| 속도 영역 | 1.0~2.25 m/s | 0.15~0.3 m/s |

단일지지 100 % 로 2 m/s 를 걷는 시스템은 훨씬 빠른 재계획이 필요하다.
**우리가 25 Hz 에서 버티는 건 우리 문제가 쉬워서지 우리가 잘해서가 아니다.**

### 2. 그런데도 100 Hz 를 권하는 이유

1. **학습 중에는 어려운 명령까지 다룬다.** residual 의 목적이 MPC 의 명령 범위를
   넓히는 것이므로(논문: vx +78 %), 학습 분포에 0.3 m/s 이상이 들어간다.
   **그 영역에서는 우리 MPC 가 100 Hz 에서도 이미 marginal** 하다 (120 초 실험:
   0.3 m/s 는 29.9 초 전도). prior 를 더 약하게 만들 여유가 없다.
2. **25 Hz 검증은 '쉬운 명령'에서만 했다.** 어려운 명령에서의 25 Hz 마진은 미확인.
3. **우리 규모에서는 비용이 안 걸린다** (아래 3절).

→ **기본 100 Hz. 50 Hz 는 검증된 예비 카드(쉬운 명령 기준 손실 없음).
   25 Hz 는 '측정된 안정 바닥'으로 기록만 하고 쓰지 않는다.**

### 3. 비용 재평가 — 우리가 생각보다 나쁘지 않다 (이전 추정 정정)

논문의 실측치와 우리 값을 나란히:

| | 논문 | 우리 |
|---|---|---|
| 1회 solve (CPU 단일 스레드) | **3.3~5 ms** (배포 시 200~300 Hz) | **7.6 ms** (중앙값) |
| 모델 복잡도 | kinodynamic 24 DoF, T=12, ADMM 25회 | SRB 13-state, N=16 |
| 1000 env × 1 step (GPU, CusADi+cuDSS) | **504.6 ms** | (배치 불가) |
| 1000 env × 1 step (CPU 10코어 낙관 추정) | 1382.3 ms | — |
| GPU 가 CPU 대비 | **겨우 2.5배** | — |

> ⚠ 이전 Q5 에서 "우리가 한 자릿수~두 자릿수 배 느리다"고 적었는데 **과장이었다.**
> 절대 시간은 **1.5~2.3배** 차이고, 심지어 그들의 모델이 훨씬 복잡하다.
> (단위 복잡도당 효율은 여전히 우리가 낮지만, 절대 비용은 같은 자릿수다.)

**GPU 병렬화의 실제 이득이 2.5배뿐**이라는 게 중요하다. 논문도 이걸 인정한다:
- 2048 env 가 VRAM 상한
- PPO 1회 업데이트에 ~12 초 → **end-to-end RL 보다 8배 느림**
- PPO 1000 iter: end-to-end 30분 vs **residual 3~4시간** (RTX 3090 + i9-10900K)

즉 **GPU 병렬화는 "공짜로 1000배"가 아니라 "고생해서 2.5배"** 다.
CusADi 코드생성 + cuDSS + IsaacGym 통합이라는 큰 공사를 하고 얻는 게 그 정도.

### 4. 우리 예산 (실측 기반)

우리 처리량 (단일 환경, 실측): **100 Hz 에서 0.76x 실시간**.

| 구성 | 5e6 samples (50 Hz 정책 = 시뮬 1e5 s) |
|---|---|
| 1 프로세스 | 36.6 시간 |
| **16 프로세스** | **2.3 시간** |
| 32 프로세스 | 1.1 시간 |

논문은 4.5e7 samples 를 썼지만 그건 **2.25 m/s + 험지 + 자기충돌 회피**까지 다루는
훨씬 넓은 과제다. 우리 범위(평지, 0.15~0.5 m/s)라면 훨씬 적은 표본으로 충분할 것.

→ **CPU 멀티프로세스 16~32 개, MPC 100 Hz. GPU 배치 QP 는 하지 않는다.**
   (학부논문 범위에서 CusADi/cuDSS 재구현은 얻는 것 대비 비용이 과하다)

### 5. ★ 논문에서 가져와야 할 다른 것들 (Hz 보다 중요할 수 있음)

**(a) 블렌딩 방식 — action space 가 결정적이다 (Fig. 6)**
논문은 세 가지를 비교했고 **관절공간 action 이 토크공간보다 확연히 우수**했다:
```
채택안 (joint action, torque blending):
   τ_residual = Kp(a + q̂ − q) − Kd·q̇          Kp = 50 N·m/rad, Kd = 3 N·m·s/rad
   τ = τ_MPC + λ·τ_residual                    λ = 0.1
```
- 토크공간 action 은 가속도 수준 제어라 탐색이 어렵고 스케일이 커서 학습이 나빴다.
- joint-joint 방식도 성능은 비슷했지만, **MPC 해가 발산하면 말도 안 되는 q_MPC 기준으로
  action 이 나가므로** joint-torque 를 택했다. (실패 모드 방어)

**(b) 정책 관측 = MPC 의 '값(value)'만** — 토크·예측상태를 관측시키면 sim-to-sim /
sim-to-real 전이가 나빠졌다 (시뮬레이터에 민감한 분포라서). 관측 o ∈ R⁵⁴ =
[p, θ, q_j, ω, v, q̇_j, φ, **V_MPC**], 출력은 다리 10개 관절만. MLP 3층 × 256 ELU.

**(c) ★ residual 이 실제로 하는 일 = 착지 보정 (§V-D, Fig. 18-19)**
- 접촉 전환 직전에 **residual 토크 비율이 급증**한다
- residual 토크는 MPC 토크와 **거의 정반대**다 (cosine similarity −0.6~−0.9)
- residual 은 **발목을 적극 사용**, heel-toe 전환이 창발적으로 나타남
- **"MPC 의 평균 착지속도는 하나의 날카로운 피크"** 인데 residual 은 두 단계로 0 에 수렴

> 이건 우리 Q3 발견(**우리 명령 착지 수직속도 −0.785 m/s**)과 정확히 같은 지점이다.
> 논문의 MPC 는 Bezier 곡선에 **착지속도 v_td 를 명시적 파라미터로** 갖고 있는데도
> (식 15) 착지가 여전히 residual 의 주 무대다. 즉 **우리가 착지속도를 0 으로 고쳐도
> residual 의 일거리가 사라지지 않는다** — 오히려 prior 를 튼튼하게 만들어 학습이 쉬워진다.

**(d) QP 반복수도 튜닝 대상** — N_QP 를 스윕해 **15 회면 충분**하지만 안전여유로 25 회
사용 (Fig. 4). 우리도 나중에 비용이 걸리면 "정확도 vs 비용" 스윕을 해볼 축이 하나 더 있는 셈.

**(e) 논문의 gait = 우리와 주기가 같다 (0.8 s)** 하지만 **이중지지가 없다**
(φ=0.5 전환). 우리 50 % 이중지지는 훨씬 보수적 — 속도를 올리려면 여기를 줄여야 할 수도.

## Q7. residual 식의 Kp/Kd 는 나중 문제인가? MPC 쪽 게인을 키우면 같이 손봐야 하나?

> "τ_MPC 는 지금 구하는 방식대로 나오고, λ 옆에 있는 게 residual 이니까 거기 Kp/Kd 는
>  아직 신경쓸 단계가 아니지? 근데 MPC 에서 kp/kd 를 키우면 얘도 결국 손 봐야 할 것 같다"

### 0. 답 — 둘 다 맞다. 단, 먼저 알아야 할 구조 차이가 있다

- **"아직 신경 안 써도 되나"** → 맞다. 우선순위는 **prior(우리 MPC) 품질**이다.
  논문 Fig. 7 이 보여준 게 정확히 그것 — prior 가 나쁘면 residual 구조가 있어도
  MPC 단독보다 못하다. 게인 조율은 residual 구현 단계 파라미터.
- **"MPC 게인을 키우면 같이 손봐야 하나"** → 맞다. 이유는 아래 3절.
- **★ 다만**: 논문의 τ_MPC 안에는 **이미 관절 PD 가 들어 있는데 우리는 없다.**
  이 구조 차이를 모르고 식을 그대로 가져오면 어긋난다.

### 1. ★ 구조 차이 — 논문의 τ_MPC 는 이미 관절 PD 다

논문 (Eq. 21):
```
τ_MPC = Kp(q_MPC − q) + Kd(q̇_MPC − q̇) + τ_RNEA
              ↑ MPC 가 예측한 '관절 궤적'을 추종하는 PD
```
가능한 이유: 논문 MPC 는 **kinodynamic** 이라 결정변수가 (q, q̇, F) — 즉 **관절 궤적
자체가 해로 나온다.** 그래서 그걸 PD 로 추종하고, RNEA(역동역학)로 피드포워드를 얹는다.

우리 (09_walk.py):
```
τ = qfrc_bias − JᵀW            (stance)
τ = qfrc_bias + Jᵀ F_임피던스    (swing)
```
우리 MPC 는 **SRB** 라 결정변수가 wrench W 뿐이다. **관절 위치라는 개념이 해에 없다.**
그래서 다리 관절에 대한 **관절공간 PD 가 아예 존재하지 않는다** (상체 PD 는 별개).

| | 논문 | 우리 |
|---|---|---|
| MPC 해 | q*, q̇*, F* (관절 포함) | W (wrench 만) |
| 토크 변환 | RNEA + **관절 PD** | **Jᵀ 사상** |
| 다리 관절 PD | 있음 (Kp 50, Kd 3) | **없음** |
| swing 제어 | 같은 관절 PD | **작업공간 임피던스** (kp 2500 N/m) |

**함의**: 논문은 residual 의 Kp/Kd 를 "MPC 가 이미 쓰던 그 게인"에서 물려받는다 —
실제로 §V 에 *"All controllers (MPC, residual, and end-to-end) used the **same gains**"*
(50 N·m/rad, 3 N·m·s/rad) 라고 못박혀 있다. 하나의 게인 세트로 전부 통일한 것.

우리는 **물려받을 게인이 없다.** residual 을 붙일 때 새로 정해야 하고, 그 값은
"논문이 50 이니까 50" 이 아니라 **우리 로봇의 토크 스케일에 맞춰** 잡아야 한다
(MIT humanoid 25 kg, 관절토크 ~5 N·m vs G1 33 kg, 무릎 ~15 N·m — 약 3배).

### 2. λ 와 Kp 는 사실상 한 덩어리다 (λ·Kp 가 residual 의 권한)

논문 (Eq. 23-24):
```
τ_residual = Kp(a + q̂ − q) − Kd·q̇        q̂ = 기본 관절자세, a = 정책 출력
τ = τ_MPC + λ·τ_residual                   λ = 0.1
```

주의할 점 두 가지:

**(a) a = 0 이어도 residual 은 0 이 아니다.** `Kp(q̂ − q) − Kd q̇` 가 남는다 —
즉 **기본자세로 끌어당기는 PD**. 논문도 인정한다: *"the residual policy will have
non-zero torques even if the network is zero-initialized. Consequently, we introduce
a weighting parameter [λ] to control the initial influence."*
→ **λ 의 역할 절반은 이 초기 편향을 억누르는 것**이다 (residual 구조의 대전제가
"초기화 시점에 baseline 을 건드리지 않는 것"이므로).

**(b) λ=0.1 이 작아 보여도 residual 토크는 MPC 토크급이다.**
논문 Fig. 18: `‖τ_residual‖ / ‖τ_MPC‖ ≈ 0.6 ~ 1.2`. 접촉 전환 근처에서 1 을 넘는다.
→ **튜닝 목표는 λ 나 Kp 의 절대값이 아니라 이 비율**이다. 우리도 그렇게 잡으면 된다:
   `λ·Kp` 를 조절해 **‖τ_res‖/‖τ_MPC‖ 가 0.5~1 근처**에 오게.

### 3. MPC 쪽 게인을 키우면 왜 residual 도 건드려야 하나 (두 경로)

**경로 ① 크기 균형** — 우리가 계획 중인 개선(Q3)은 MPC/스윙 쪽 권한을 키운다:
```
스윙 kp: 2500 → Λ·ω_n² ≈ 14,000~103,000 N/m   (최대 41배)
```
그러면 baseline 토크가 커지므로, **같은 λ·Kp 로는 residual 의 상대 비중이 줄어든다.**
2절의 비율을 유지하려면 λ·Kp 도 같이 올려야 한다.

**경로 ② 임피던스 경쟁 (이쪽이 더 미묘하다)** — 스윙 다리를 매우 뻣뻣하게 만들면
그 다리는 사실상 **작업공간 위치 서보**가 된다. 거기에 residual 이 관절토크를 더해도
**그 강성이 되밀어서** 실제 움직임이 잘 안 생긴다. 즉 **같은 토크를 넣어도 효과가 준다.**

> 논문은 이 문제가 우리보다 작다. 그쪽은 baseline 도 residual 도 **같은 관절 PD 안**에서
> 살기 때문. 우리는 baseline 이 작업공간 임피던스인데 residual 은 관절공간이라
> **서로 다른 공간에서 싸우는** 구조가 된다 — 설계할 때 의식해야 할 지점.

### 4. 그래서 순서는

1. **prior 부터 완성한다** (지금 할 일): 착지속도 0, 스윙 Λ 스케줄, 착지 램프.
   논문 Fig. 7 의 교훈 = prior 품질이 지배 변수.
2. **prior 를 얼린 뒤** residual 의 λ·Kp 를 정한다 — `‖τ_res‖/‖τ_MPC‖ ≈ 0.5~1` 기준으로.
3. 그때 action space 도 결정 (논문 Fig. 6: **관절공간 >> 토크공간**).

**순서를 지켜야 하는 이유**: prior 를 바꾸면 그 위에 학습된 정책이 무효가 된다.
논문은 residual 이 MPC 가중치 ±100 % 변화(Fig. 17)나 gait/스윙높이 변경(Fig. 12, 16)에
꽤 강건함을 보였지만, **스윙 강성 40배 변경은 그 검증 범위를 한참 넘는다.**

### 5. 한 줄 요약

> **지금은 신경 쓰지 말되, "나중에 정할 값"이 아니라 "prior 가 확정된 뒤에 그에 맞춰
> 정할 값"으로 기억해 둘 것.** 그리고 우리는 논문과 달리 **다리 관절 PD 가 없어서
> 물려받을 게인이 없다** — residual 을 붙일 때 새로 설계해야 하는 항목이다.

## Q8. 왜 다리를 벌리고(팔자로) 걷나?

> 뷰어로 보니 보행 중 다리가 벌어진 자세가 된다.

### 0. 답 — capture point 항이 매 착지마다 발을 바깥으로 민다

착지 48회를 뜯어 raibert 식의 항별 기여를 측정 (0.3 m/s, 권장 구성):

| 항 | 왼발 | 오른발 |
|---|---|---|
| 공칭 오프셋 (side_offset) | +11.8 cm | −11.9 cm |
| **capture `v_y/ω₀`** | **+6.7 cm** | **−6.5 cm** |
| anchor `k(y−y₀)` | −1.0 cm | −0.8 cm |
| **실제 발 − CoM** | **+14.4 cm** | **−16.1 cm** |

보폭 너비 **23.7 cm(공칭) → 30.5 cm = 129 %**. 벌어진 6.8 cm 가 capture 기여와 일치.

**공칭 자세는 정상이다**: G1 힙 roll 축 ±11.6 cm vs 초기 발 ±11.9 cm — 힙 바로
아래로 0.4 cm 차이뿐. **걸으면서 벌어지는 것**이지 처음부터 벌린 게 아니다.

### 1. 왜 부호가 항상 '바깥'인가 (기전)

LIP 횡 동역학: `ÿ = ω₀²(y − p_foot)` — CoM 은 **지지발에서 멀어지는 쪽으로 가속**한다.
오른발 stance 동안 CoM 은 왼쪽으로 가속하므로, **왼발이 착지하는 순간 CoM 은 항상
왼쪽으로 움직이고 있다** (실측 v_y ≈ 0.26 m/s). capture point 는 *"그 움직임을
멈추려면 어디를 딛어야 하나"* 의 답이므로 → 왼쪽으로 멀리 딛으라고 한다.
오른발도 대칭으로 같은 일. **그래서 양발이 각자 자기 쪽으로 밀려 벌어진다.**

**그런데 우리는 멈추고 싶은 게 아니다.** 주기 보행의 횡 방향은 좌우로 계속 흔들리는
**리미트 사이클**이 정상인데 "정지" 게인을 쓰니 매 스텝 과하게 딛는다.
→ Q4 §5 에 적어둔 caveat (*capture point 는 '지금 멈추기'의 답, 주기 보행의 최적
step-to-step 게인은 T_stance 에 의존 — H-LIP*) 이 **눈에 보이는 형태로 드러난 것**.

129 % 에서 멈추는 이유: anchor 항(−1 cm, 중앙 되당김) + MPC sway 참조 추종이 브레이크.

### 2. 최근 변경 탓인가? — 아니다 (모든 구성에 있다)

| 구성 | 보폭 너비 | capture 기여 |
|---|---|---|
| baseline 0.15 | 27.8 cm (117 %) | ±4.5 cm |
| baseline 0.30 | 26.9 cm (113 %) * | ±4.1 cm |
| sl+lam 제자리 | 26.6 cm (112 %) | ±4.6 cm |
| sl+lam 0.15 | 26.2 cm (111 %) | ±4.4 cm |
| **sl+lam 0.30** | **30.5 cm (129 %)** | **±6.6 cm** |

\* baseline 0.3 은 29.9 s 에 전도하므로 측정창(t 6~25 s)이 '죽기 직전' 구간 — 공정 비교 아님.

**원래부터 111~117 % 로 벌리고 걸었다.** 0.3 + sl+lam 만 129 % 로 두드러지는데,
그 구성이 **유일하게 0.3 을 120 초 완주하는 구성**이다.

### 3. 나쁜 건가? — 양면이다

- **이득**: 넓은 지지면 = 횡 안정 마진 ↑. **0.3 이 살아남는 이유의 일부**로 보인다
  (횡 동역학이 격해질수록 v_y ↑ → capture 기여 ↑ → 더 벌림 → 더 안정. 자기보상 루프)
- **대가**: 횡 CoM 이동거리 ↑ → **sway(우리가 잡으려는 흔들림) 증가**, 힙 roll 토크 증가,
  보행 모양 부자연스러움
- **증상으로서의 의미**: Q4 §2 의 **두 루프 경쟁**(MPC sway 참조 + capture 착지가
  같은 횡 방향을 동시 제어)이 가시화된 것

### 4. 고친다면 (지금은 권하지 않음)

| 방법 | 내용 | 평가 |
|---|---|---|
| (a) 횡 축만 게인 축소 | y 축 capture 게인을 1/ω₀ 보다 작게 | 간단하나 **민감** — gait.py 주석에 이미 "이 게인은 민감하다, 1/ω₀ 가 최선이었고 ±변경 모두 악화" 기록 |
| (b) H-LIP 식 | `(v_y − v_y*)/ω₀` — 목표 리미트사이클의 착지 속도 v_y* 를 빼서 '정지'가 아니라 '주기 유지' 기준으로 | **원리적으로 옳음**. 단 자유 LIP 해석값 v*=0.56 m/s vs 실측 0.26 m/s — MPC 가 이미 개입 중이라 해석값 그대로 쓰면 과보정 |
| (c) 놔둔다 | 지금 안정을 사고 있는 중 | **현재 권장** |

**권장 순서**: 먼저 **접촉 인지 계층**(wrench 램프·조기접촉)을 넣는다 →
착지 외란이 줄어 **v_y 자체가 작아지고** → capture 기여가 자연히 줄어 보폭이 좁아진다.
게인을 직접 건드리는 건 그 다음. **원인(착지 외란)을 먼저 치고 증상(게인)은 나중에.**

### 5. reference 는 어떻게 하나 — **보폭이 아예 넓어질 수 없는 구조**

코드 확인 결과 (`My_Controller/src/SwingFootPlanner.cpp`):

**(a) 횡 방향에 측정 속도가 안 들어간다** (Q4 §1 과 같은 이야기)
```cpp
const Vec3<double> previewVelocity_B(currentPlanarCommand.x(),   // ← 명령 속도
                                     currentPlanarCommand.y(), 0.0);
const Vec3<double> step_W = Rz(translationYaw_W) * previewVelocity_B * previewTime;
```
직진 명령이면 `y_dot = 0` → **횡 방향 보폭 기여가 0**. 우리 `v_y/ω₀` 같은 항이 없다.

**(b) 공칭 횡 오프셋은 '한 번 정하고 얼린다'** (`ensureNominalFootOffsets`)
```cpp
if (allValid) { return; }                        // ← 이미 정해졌으면 재계산 안 함
...
Vec3<double> offset_B = R_BW * (footPos_W − footCenter_W);
offset_B.x() = 0.0;  offset_B.z() = 0.0;         // y 만 남김
```
또는 YAML 로 명시 (MIT):
```yaml
nominal_foot_offsets_B:
  - [0.0,  0.075999602, 0.0]      # 왼발 +7.6 cm
  - [0.0, -0.075999602, 0.0]      # 오른발 −7.6 cm
```

**(c) 클램프는 '교차 방지'일 뿐 넓히지 않는다**
```cpp
if (nominalLateralOffset > 0.0) plannedOffset_B.y() = std::max(plannedOffset_B.y(), 0.0);
else if (nominalLateralOffset < 0.0) plannedOffset_B.y() = std::min(plannedOffset_B.y(), 0.0);
```
중심선을 넘지만 못하게 하는 하한(우리 `min_y_sep=0.06` 에 해당). **상한이 없어도
상관없다 — 넓힐 항 자체가 없으니까.**

#### 숫자 비교가 결정적이다

| | 힙 폭 | 공칭 발 폭 | **보행 중 발 폭** |
|---|---|---|---|
| **reference (MIT)** | ±8.2 cm | **±7.6 cm** (힙보다 **안쪽** 0.6 cm) | **±7.6 cm 고정** |
| **우리** | ±11.6 cm | ±11.9 cm (힙보다 바깥 0.4 cm) | **±13~15 cm (111~129 %)** |

reference 는 **힙선보다 안쪽으로, 일정하게** 딛는다. 사람 보행에 가까운 모양이고
횡 CoM 이동거리도 작다. 우리는 **바깥으로, 속도에 따라 점점 더** 벌어진다.

#### 왜 그게 가능한가 — 대가를 다른 데서 치른다

횡 안정을 **전부 MPC 가 맡기 때문**이다 (py 가중치 G1 42,000 / MIT 1,009,300 —
Q3 §4 참고). 발디딤에 피드백이 없으니 **넓어질 기전 자체가 존재하지 않는다.**

즉 이건 "reference 가 더 잘한다"가 아니라 **설계 트레이드오프의 반대편**이다:

| | 횡 안정 담당 | 보폭 | 그 대가 |
|---|---|---|---|
| reference | MPC 단독 | 좁고 일정 | 극단적 위치 가중치 필요, 발디딤의 외란 대응 능력 없음 |
| 우리 | MPC + capture 발디딤 | **속도 따라 넓어짐** | 외란에 발로 대응 가능, 대신 sway·모양 손해 |

#### 그래서 우리에게 주는 결론

**capture 항을 그냥 빼면 안 된다** — 그건 우리의 주 횡 안정기다 (빼려면 reference 처럼
MPC 가중치를 전면 재설계해야 하고, 그건 21절에서 배운 "패키지는 통째로 와야 한다"의
반복이 된다). 4절의 권장 순서(**접촉 인지 → v_y 감소 → 보폭 자연 축소**)가 여전히 유효하다.

다만 **reference 가 '±7.6 cm 고정'이라는 상한 개념을 가진 건 참고할 만하다** — 우리도
capture 의 횡 기여에 **상한(예: ±3 cm)만 씌우는** 절충이 가능하다. 게인을 줄이는 게
아니라 **큰 외란일 때만 발이 나가게** 하는 것이라 평상시 보폭은 좁히고 외란 대응은
남긴다. (미검증 아이디어 — 접촉 인지 작업 뒤에 시험할 후보)

### 6. (검증 완료) capy=±3 cm 실측 — 켤 가치 있는 옵션, 기본값은 보류

`--capy 0.03` 구현 후 120 초 배터리 + 보폭/진동 정량 비교 (sl+lam 기준):

| 지표 | 무제한 | **capy 3 cm** |
|---|---|---|
| 생존 (제자리/0.15/0.3) | ✓/✓/✓ | **✓/✓/✓** (손실 없음) |
| 보폭 (0.3) | 30.5 cm (129 %) | 28.7 cm (121 %) |
| 보폭 (제자리/0.15) | 26.6 / 26.2 | 26.2 / 26.1 (거의 불변) |
| **pitch (0.15)** | 6.54° | **3.59° (−45 %)** |
| 전구간 y 진폭 (0.15) | ±9.1 cm | **±3.3 cm** (느린 횡 weave 소멸) |
| roll (0.15 / 0.3) | 3.23° / 5.38° | 4.58° / 6.57° (**악화**) |
| pitch (제자리 / 0.3) | 3.77° / 7.08° | 3.55° / 7.35° (불변) |

**배운 것 둘**:
1. **닫힌 루프는 산술대로 안 좁아진다** — 착지 시점 capture 기여가 ±4.4~6.6 cm 라
   상한 3 cm 면 보폭이 3~7 cm 줄어야 하는데 실측 0.4~1.8 cm. 바깥 딛기를 막으면
   횡 진동이 덜 잡혀 v_y 가 커지고, sway 참조가 실제 발을 따라가며 폭을 되찾는다.
2. **진짜 이득은 예상 밖의 곳에서** — 0.15 의 느린 횡 weave(전구간 y ±9.1 cm)가
   사라지고 pitch 가 반토막. 과보행→과요동→과보행의 저주파 사이클을 상한이 끊은 것.
   대가는 roll 진폭 +1.2~1.3° (좁아진 지지면의 예상된 비용) — 22절에서 0.3 붕괴가
   roll 모드였으므로 **취약축의 마진을 깎는 방향**이라 기본값 편입은 보류.

**판정**: 저속 순항 품질(흔들림·모양)이 중요하면 켜고, 0.3+ 를 밀어붙일 때는 끈다.
접촉 인지 작업(착지 외란 → v_y 감소) 후 재평가 — 그때는 상한이 더 잘 들을 것.

## Q9. 왜 0.3 m/s 이상이면 무너지나? reference 는 같은 G1 으로 0.6 을 하는데?

> (+ "residual RL 이 메꾼다는 건 아니다 — 논문 저자의 convex MPC 자체가 1.5~2 m/s 다.
>  최소한 1 m/s 는 해야 한다")

### 0. 먼저, 이전 답이 틀렸다

23절까지 나는 이 벽을 **"발이 작아서 CoP(피치) 권한이 모자라다"** 고 설명하고
"남는 건 residual RL 의 몫" 이라고 썼다. **둘 다 틀렸다.**

- reference 의 **검증된 MIT 설정은 발이 우리보다 작다** (`half_length 0.065 /
  half_width 0.01` vs 우리 실측 `l_t 0.12 / l_h 0.05 / w 0.025`) — 그런데 1~2 m/s.
  **발 크기는 벽이 아니다.**
- 논문의 MPC baseline 자체가 1.5~2 m/s 다. 우리 0.35 를 "모델 기반의 한계" 라 부르고
  RL 에 넘기는 건 **구현 결함을 원리 탓으로 돌리는 것**.

(CoP 박스를 잘못된 frame 에서 쟀을 가능성도 의심해 확인했으나, site 가 body 원점에
있어 `l_t/l_h` 는 정확했다 — 이건 버그가 아니었다.)

### 1. 붕괴 기전 측정 (0.4 m/s, 6.7 s 전도)

| 지표 | 0.3 (완주) | 0.4 (전도) |
|---|---|---|
| **착지점 오차** | 1.9 cm | **8.7 cm** (최대 18.5) |

### 2. 격리 실험 — 범인은 '스윙 반작용'

| 조건 (0.4 m/s) | 전도 | CoP | swing포화 | 착지오차 |
|---|---|---|---|---|
| A 기준 | 6.7 s | 27.0 % | 10.1 % | 8.7 cm |
| B **스윙 힘상한 400→1000 N** | **4.6 s (악화!)** | 16.8 % | 0.0 % | 9.8 cm |
| C 스윙 0.2→0.28 s | 9.4 s | 25.9 % | 4.5 % | 6.0 cm |
| D 둘 다 | 11.6 s | 26.7 % | 0.2 % | 4.8 cm |
| **다리 질량 1/3** | **25 s 생존 ✓** | 발가락 33.4→**5.5 %** | — | — |

**(a) 힘 상한은 보호 장치였다.** 1000 N 으로 풀면 발은 목표에 정확히 가는데(포화 0 %)
**더 빨리 넘어지고 착지오차도 커진다** — 발이 정확해진 대가로 **몸이 더 세게 걷어차인다.**
→ "발을 정확히 놓기" 와 "몸을 안 흔들기" 는 상충하고, 우리는 이미 최적점 근처였다.

**(b) 다리를 가볍게 하면 0.4 가 산다.** 발가락쪽 CoP 포화가 33.4 → 5.5 % 로 6배 감소.
→ CoP 를 고갈시키는 건 **속도가 아니라 무거운 다리를 휘두르는 반작용**.

### 3. ★ 그래서 reference 와 뭐가 다른가 — gait 타이밍

스윙 최고 가속도는 `a = 6L/T_sw²` (smoothstep). **T_sw 가 짧으면 제곱으로 커진다.**

| | 주기 | 스윙 | 스윙비율 | 이중지지 | **a_peak** | 반작용 |
|---|---|---|---|---|---|---|
| **우리(구)** | 0.8 s | **0.2 s** | 25 % | 50 % | **120·v** | **863·v N** |
| ref (G1) | 0.7 s | 0.3 s | 43 % | 14 % | 46.7·v | 336·v N |
| ref (MIT) | 0.5 s | 0.17 s | 34 % | 32 % | 103.8·v | (다리 4배 가벼움) |

**같은 속도에서 우리 스윙이 2.6 배 격렬했다** (0.4 m/s: 345 N vs 134 N).
우리가 스윙 kp 를 2500 까지 올려야 했던 것(Step5 디버깅 1차)도 사실 **원인(너무 빠른
스윙) 대신 증상(추종 실패)을 보상**한 것이었다.

### 4. 고친 것 — 두 개가 반드시 같이 가야 한다

**① `--sf 0.57`** (stance_frac 0.75→0.57, 스윙 0.2→0.34 s)
→ 0.4 에서 CoP 포화 **50.6 % → 12.6 %**, 생존 6.7 → 21.4 s.
**단독으로는 부족**: 이중지지가 50→14 % 로 줄어 횡 균형이 깨짐 (y 진폭 23 cm).

**② `--qpy 300`** (Q_py 50→300)
→ 줄어든 이중지지의 대가를 MPC 횡 제어로 메움. y 진폭 **23.2 → 5.9 cm**.
(reference 의 py/px 비 = 5~14, 우리 기본은 1 — Q3 §4 에서 본 그 비율)

> **21절의 "패키지는 통째로 와야 한다"가 또 확인됐다.** 안전판(이중지지)을 걷어냈으면
> 그만큼 횡 제어를 강화해야 한다. 하나만 바꾸면 다른 데서 무너진다.
