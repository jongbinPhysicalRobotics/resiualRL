## Q1. 비대칭이 안 고쳐지는 이유 — MPC 가 '없는 roll 모멘트' 로 바로잡으려 한다 + mx = 0 (`foot=mx0`) A/B

**결론** (측정): ref 발 모델에서 MPC 는 두 발 모두 **같은 부호의 roll 모멘트** (평균 −0.75 N·m) 를 계속 요청하고,
위상을 맞바꾸면 (`sideswap`) 부호도 같이 뒤집힌다 — 쏠림을 발목 roll 로 바로잡으려는 명령인데 **선 접촉 발은 이걸 못 준다**
(9/26 Q5·9/25 논의). MPC 는 고치고 있다고 믿지만 실제로는 사라진다 → 비대칭이 유지된다 (추론).
mx = 0 등식만 넣으면 (`mx0`) 걷기가 무너지고 (0.6 에서 17 s, 추종 67 %), **mx0 + 착지 속도 되먹임 (rai 0.2)** 이면
네 목표 모두 완주하며 **전진 하중비 1.38 → 1.11** 로 대칭에 가까워진다.

### 1. 부호 있는 발 roll 모멘트 Mx^F (0.6 m/s, 창 8 ~ 20 s, 하중 실린 디딤)

| | L 평균 | R 평균 | vy | 하중 L / R |
|---|---|---|---|---|
| 기준 | **−0.79** (+ 부호 15 %) | **−0.73** (39 %) | −0.061 | 132 / 199 N |
| sideswap | **+0.73** (67 %) | **+0.76** (83 %) | +0.053 | 184 / 137 N |

### 2. 덤 — 서기 수정 (9/26 Q6) 이 걷기 시작을 바꾸고 있었다 → 수정

걷기도 시작 전 1 s StandingSettle (FSM 서기) 를 거치는데, Q6 의 서기 yaw hold · 자중 보상이 거기에도 걸려
시작 자세가 조금 달라졌고 **0.6 m/s 가 20.0 s 에 전도** (재현 확인). 서기 수정은 **서기가 요청된 경우만** 걸도록
([controller.py](../MPC/src/casadi_mit/controller.py) `stand_fix`) → 걷기 0.6 원래 궤적 복귀 (120 s · 85 %), 서기 드리프트 2.7 mm 유지.
덤의 교훈: **0.6 m/s 는 시작 자세 변화에 20 s 로 넘어질 만큼 경계에 있다** (명령 1e-4 흔들림엔 버텼지만).

### 3. A/B (120 s, 램프 + yawref, 서기 수정 격리 후) — `R/L` = 좌우 명령 Fz 중앙값 비 (1 = 대칭)

|---|---|---|---|---|---|---|

| rai 0.2 | ✓ 92 % | ✓ 92 % | ✓ 73 % | ✓ 100 % | 1.34 | −0.07 |

(횡 걷기의 R/L 은 진행 방향상 원래 비대칭이라 대칭 지표로 쓰지 않음.)

### 4. 읽기

- **mx0 단독이 무너지는 이유 (추론)**: roll 통로를 막으면 MPC 에 옆 방향 복원 수단이 거의 없다 (선 발이라 CoP 도 옆으로 0).
  남는 건 착지 위치뿐인데 reference 착지 계획엔 측정 속도 항이 없다 (9/26 Q8) → 옆 되먹임 0 → 느려지고 넘어짐.
- **mx0 + rai 가 맞는 짝**: 물리적으로 불가능한 통로 (roll) 를 막고, 실제로 가능한 통로 (발걸음) 에 되먹임을 준다.
  **전진 하중비 1.11** 로 비대칭 대부분 해소, 세 목표 유지. 추종은 rai 단독 (92 %) 보다 약간 낮다 (89 %).
- **남은 것**: vy −0.05 옆 드리프트 (속도 되먹임뿐이라 위치는 안 잡음). 회전 τ/lim 스파이크 1400 (1 회 순간값, 포화 비율 0.32 는 다른 구성과 같음).
- **판단**: mx0 + rai 0.2 를 **채택 후보** — 렌더 확인 (`--foot mx0 --rai 0.2`) 후 casadi_mit 기본값 전환 결정. 기본은 아직 ref · rai 0.

## Q2. 옆으로 벗어날 때 보정하는 항 — 착지 위치 항 (`ypos`) 은 실패, MPC 참조를 경로선에 붙잡는 항 (`ypath`) 은 성공

**결론** (측정): 드리프트의 정체는 **게걸음** — 몸 방향은 목표와 +1° 로 맞는데 진행 방향이 몸보다 −8° (ref) / −6° (mx0+rai)
틀어져 초당 ~5 cm 씩 오른쪽으로 간다. 걷기 시작 1 s 안에 생긴 옆 속도가 유지되는 것 (reference 는 옆 위치 참조를 매번
측정값에 재고정 → 복원력 0, 글 6.1). MATLAB convex_mpc.m 식 착지 위치 항 (`p_y += 0.3·y_com`, MPC_NOTES §12-7) 은
작으면 못 이기고 크면 튕겨 실패. **MPC 참조의 옆 위치를 경로선 쪽으로 당기는 `ypath`** 는 게걸음을 없애고
옆걸음 추종을 67 → 100 % 로 올린다. rai 와 짝으로 써야 회전도 버틴다.

### 1. 방법

- 경로선 = 걷기 시작 CoM 에서 **명령 속도를 목표 yaw (yawref) 방향으로 적분** ([controller.py](../MPC/src/casadi_mit/controller.py) `path_W`).
  옆 이탈 e = heading 왼쪽 성분 (CoM − 경로).
- `ypos=k` (착지): 착지 목표 옆 += k·e, ±5 cm 클램프 — "밀린 쪽으로 더 딛기" (+부호, LIP 로 확인).
- `ypath=a` (MPC): 참조 seed 의 옆 위치를 경로선 쪽으로 a·e 만큼 — MPC 의 옆 위치 가중치 (1e6) 가 되돌린다. a = 1 이면 경로선 그대로.

### 2. 결과

`ypos` (mx0 + rai 0.2, 20 s): k 0.05 → 이탈 계속 증가 (11 s 에 −456 mm), k 0.15 → 8.2 s 전도 (vy +0.34 로 튕김), 0.3 → 6.9 s 전도.

`ypath` (120 s, 램프 + yawref):

| 구성 | 전진 0.6 | 횡 0.3 | 회전 1.3 | 전진 R/L | vy |
|---|---|---|---|---|---|
| ref (기준) | ✓ 85 % | ✓ 67 % | ✓ 100 % | 1.38 | −0.07 |
| ypath 0.3 | ✓ 89 % | ✓ **100 %** | **✗ 5.1 s** | 0.89 | −0.01 |
| **rai 0.2 + ypath 0.3** | ✓ **92 %** | ✓ **100 %** | ✓ 100 % | 0.89 | −0.01 |
| mx0 + rai 0.2 + ypath 0.3 | ✓ 88 % | ✓ 100 % | ✓ 100 % | 0.84 | 0.00 |
| mx0 + rai 0.2 + ypath 0.1 | ✓ 88 % | ✓ 100 % | ✓ 100 % | 0.87 | 0.00 |

20 s 추가: ypath 0.1 / 0.3 / 1.0 모두 게걸음 0.0 ~ 0.1°, 12 s 옆 이동 +2 ~ +17 mm (기준 −579 mm).

### 3. 읽기

- 착지 위치 항이 안 먹힌 이유 (추론): 드리프트는 외란이 아니라 **꾸준한 옆 속도** 라 발걸음 P 보정은 게인을 올려야 하는데,
  선 발 · 짧은 스윙 (0.17 s) 에선 게인을 올리면 과보정 진동. MPC 는 매 풀이 (14 ms) 힘으로 연속 보정한다.
- 게걸음이 사라지자 하중비가 **반대로 (0.89, 왼발 쪽)** — 비대칭이 드리프트만의 결과가 아니었다 → Q3.

## Q3. 남은 하중 비대칭의 뿌리 = O1 (주기 시작 기준 접촉표) — `slide` 로 R/L 1.00

**결론** (측정): 게걸음을 없앤 뒤에도 하중비는 위상을 맞바꾸면 뒤집혔다 (0.88 ↔ 1.22). 착지 폭 (62 / 63 mm) · 옆 속도 (0.000) 는
이미 대칭 → 남은 비대칭은 **MPC 가 두 다리를 다르게 보는 곳** — 7.2 절의 O1: 지평이 매번 **주기 시작 t0 부터 한 주기**라
왼발 스윙은 표 중간 (0.08 ~ 0.25 s), 오른발 스윙은 표 끝 (0.33 ~ 0.5 s) 에 놓인다 (코드 사실). 접촉표를 **지금부터** 로
(`fix=slide`) 바꾸면 **R/L 1.00, 위상 맞바꿔도 1.01.**

### 1. 30 s 확인

| 구성 | R/L | sideswap 시 |
|---|---|---|
| rai 0.2 + ypath 0.3 (주기 시작 표) | 0.88 | **1.22** (뒤집힘) |
| **slide** + rai 0.2 + ypath 0.3 | **1.00** | **1.01** (불변) |
| 〃 + OSQP 4000 회 | 0.99 | |

### 2. 120 s 검증

| 구성 | 전진 0.6 | 0.5998 | 횡 0.3 | 회전 1.3 | 0.5 | R/L | roll σ | 포화 |
|---|---|---|---|---|---|---|---|---|
| **slide + rai 0.2 + ypath 0.3** | ✓ 90 % | ✓ 90 % | ✓ 100 % | ✓ 100 % | ✓ 92 % | **1.01** | **0.006** | **0.001** |
| slide + mx0 + rai 0.2 + ypath 0.3 | ✓ 85 % | ✓ 85 % | ✓ 100 % | ✓ 100 % | ✓ 86 % | 0.99 | 0.005 | 0.000 |

기준 (ref) 대비: roll σ 0.008 → 0.006, 마찰 사용 p95 0.31 → 0.21, 전진 토크 포화 0.009 → 0.001 — 걸음 품질 전반이 좋아진다.

### 3. 대가 · 역사

- `slide` 는 접촉 패턴이 매 풀이 바뀌어 **cold start 0.99** → 단독 실행 MPC 풀이 중앙 **44 ms (기존 18 ms 의 2.5 배)**.
  Python 에선 둘 다 실시간이 아니지만 (주기 14 ms) 실시간화할 때 부담 (C 코드 생성 · warm start 대책 필요).
- 9/25 Q2 에선 `slide` 가 반복 200 회에서 6.3 s 전도였다 — 옆 보정 (rai + ypath) 이 들어가자 200 회로도 안정 (추론: 그땐 드리프트 + O1 제거의 과도가 겹쳤을 것).
- reference 가 O1 을 둔 이유 (warm start 유지로 추정, 9/25 Q3) 와 정확히 맞바꿈이다: **대칭 ↔ 풀이 비용.**

### 4. 판단 (사용자 결정 대기)

- 기본값 후보: **`fix=slide+yawref, rai=0.2, ypath=0.3`** (ref 발). mx0 는 물리적으로 맞지만 추종 −5 %p — 옵션 유지.
